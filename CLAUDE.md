# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Product context

SaniMe is a mobile app (Expo/React Native) that digitizes the German "Hilfsmittelversorgung" process (medical supply procurement via prescription + statutory health insurance). The customer just photographs documents (Rezept, Krankenkassenkarte); OCR runs entirely on-device (`lib/ocr/`), and a NestJS/Postgres backend (`apps/backend/`) handles product matching, insurance submission, and order tracking. The app runs against this real backend end-to-end — nothing in `store/` is mocked anymore (the last mocks, `lib/mockOcr.ts` and `lib/mockKundenArchiv.ts`, were deleted once the backend cutover landed). See "Backend (`apps/backend/`)" below for that side; the rest of this file covers the mobile app.

Rezept-Scan is no longer the only way to get a Versorgung: tapping the dashboard's `+` opens an entry chooser (`/einstieg`) with Katalog-Browsing (self-pay items, no prescription needed) and Krankheitsbild-Erfassung (describe a condition — by search or voice — and get product recommendations) as siblings. See "Katalog-Browsing, Krankheitsbild-Erfassung & Sprach-Eingabe" below for that whole feature; it's woven through the FSM described next, not bolted on separately.

Product/UX rules that should inform any feature work:
- One task and one primary CTA per screen; always allow Back/Forward with visible progress.
- Automate over form input — never ask the user for information that could be derived (OCR, defaults, recommendations).
- Every OCR/derived field must stay user-editable; OCR output is never final.
- Error messages must state a concrete next step for the user (German, e.g. "Wir konnten dein Rezept nicht vollständig erkennen. Bitte überprüfe die markierten Felder." — not "OCR Error").
- Health/insurance data (prescription photos, diagnoses, insurance IDs) is highest-sensitivity: never log it, send it to analytics, or store it unencrypted.
- New UI must meet WCAG 2.1 AA: 44×44 touch targets, screen reader labels, logical focus order, sufficient contrast, Dynamic Type support.
- The product catalog (`Produkt` type) is a placeholder during development — never hardcode real manufacturer/pricing/Hilfsmittelnummer data as if it were production data.
- A product with no Hilfsmittelnummer (`Produkt.hilfsmittelNr` is optional) is a self-pay ("Selbstzahler") item — its flow skips Krankenkassenkarte/insurance entirely, never the reverse.

```bash
npm run start       # expo start — Metro bundler, scan QR or press i/a for simulator
npm run ios         # expo run:ios — build & launch native iOS
npm run android     # expo run:android — build & launch native Android

```

`npm run lint` requires `.eslintrc.js` (extends `expo`) at the repo root — this file didn't exist before and lint silently failed with no config found; it's checked in now, don't delete it.

Jest is configured (`jest.config.js`, `jest-expo` preset) with a `test` script; run with `npm run test`. Tests are co-located next to source as `*.test.ts` — under `lib/ocr/` (parsers/validators/mapper) and `packages/@sanime/domain/` (the FSMs). No app-side integration/E2E/accessibility test automation exists — see "Manual/interactive testing" below for that.

Always run `npm run typecheck` and `npm run lint` after app changes; also run `npm run test` when touching `lib/ocr/` or `packages/@sanime/domain/`. For interactive verification (actually tapping through screens), see "Manual/interactive testing" below.

**Backend** (`apps/backend/`, proxied from the root via npm workspaces — run from the repo root, not `cd apps/backend`):
```bash
npm run backend:dev          # node --watch ts-node — NOT `nest start`/`nest build`, see the gotcha below
npm run backend:typecheck    # tsc --noEmit -p tsconfig.build.json
npm run backend:lint         # eslint "{src,test}/**/*.ts"
npm run backend:test         # jest — unit/integration, needs the docker-compose Postgres running
npm run backend:test:e2e     # jest --config ./test/jest-e2e.json
npm run backend:db:generate  # drizzle-kit generate — after any schema/*.ts change
npm run backend:db:migrate   # drizzle-kit migrate
npm run backend:db:seed      # organizations → admin → catalog → customers → retention-policy seeds, in that order
```
`docker compose -f apps/backend/docker-compose.yml up -d` starts Postgres + MinIO (S3-compatible object storage for document uploads) before `backend:dev`/`backend:test*`. Copy `apps/backend/.env.example` to `apps/backend/.env` first (`DATABASE_URL`, `STORAGE_*`, `VERIFICATION_CODE_PEPPER`, `ADMIN_JWT_SECRET` — the last two must be real values, not the checked-in placeholders, outside local dev).

**Critical gotcha**: `apps/backend/src/main.ts` boots fine under `ts-jest`/`tsx` but a plain `nest build && node dist/main.js` (or `nest start`) crashes with `ERR_MODULE_NOT_FOUND` resolving `@sanime/domain/types` — `@sanime/domain` is deliberately raw, unbuilt TypeScript (same convention as `@sanime/design-system`), and plain Node's native TS/ESM handling can't follow its extensionless internal imports the way `ts-node`'s require hook can. `start`/`start:dev` are already wired to `ts-node` for this reason — don't "fix" them back to `nest start`/`nest build`.

Always run `npm run backend:typecheck` after backend changes; run `npm run backend:test`/`backend:test:e2e` when touching anything under `apps/backend/src/modules/` or `packages/@sanime/domain/` (the FSM the backend and app both import).

## Architecture

**Stack**: Expo (SDK 57) + expo-router (file-based routing, typed routes enabled) + React Native 0.86 + NativeWind (Tailwind for RN, see `tailwind.config.js`/`global.css`) + Zustand for state + AsyncStorage for persistence. Path alias `@/*` maps to repo root (`tsconfig.json`), though existing code consistently uses relative imports (`../../types`) instead — match that convention, not the alias.

The onboarding-to-checkout flow is implemented end-to-end as an explicit **state machine**, not a hardcoded screen chain, and it now has three parallel entry paths converging and diverging at well-defined points rather than one linear chain:
- **Rezept** (original path): Willkommen → Leistungsübersicht/consent → Rezeptaufnahme → Rezeptprüfung → Krankenkassenkarte → Datenprüfung → Versorgungsauswahl → Termin → Zusammenfassung → Checkout → Dashboard.
- **Katalog-Selbstzahler**: Willkommen → Leistungsübersicht → (pick a no-Hilfsmittelnummer product in `/katalog`) → Termin → Zusammenfassung → Checkout — skips Rezept/Krankenkasse/Datenprüfung/Versorgungsauswahl entirely.
- **Krankheitsbild**: Willkommen → Leistungsübersicht → Krankheitsbild-Erfassung → Krankheitsbild-Empfehlung → then forks again by the *picked* product's Hilfsmittelnummer: a HiMi pick rejoins the Rezept chain at Rezeptaufnahme (same downstream screens/back-navigation as if it'd come from `/katalog`'s HiMi branch), a self-pay pick goes straight to Termin like the Katalog-Selbstzahler path.

The FSM itself lives in `packages/@sanime/domain/onboarding.ts` — a workspace package imported by **both** the app and `apps/backend/` — not in `store/`, so a client-illegal transition is guaranteed server-illegal too. Read this section together with that file before touching any onboarding/scan screen or the backend's `OnboardingService`.

### State machine (`packages/@sanime/domain/onboarding.ts` + `store/onboardingStore.ts`)

- **`packages/@sanime/domain/onboarding.ts`** — pure functions only, no React/Zustand/AsyncStorage/NestJS import (isolated, imported unmodified by both runtimes):
  - `OnboardingStatus` — the 14-state union (`WILLKOMMEN`, `LEISTUNGSUEBERSICHT`, `KRANKHEITSBILD_ERFASSUNG`, `KRANKHEITSBILD_EMPFEHLUNG`, `REZEPT_AUFNAHME`, `REZEPT_PRUEFUNG`, `KRANKENKASSE_AUFNAHME`, `DATENPRUEFUNG`, `VERSORGUNGSAUSWAHL`, `TERMINPLANUNG`, `ZUSAMMENFASSUNG`, `CHECKOUT`, `CHECKOUT_FEHLGESCHLAGEN`, `ABGESCHLOSSEN`), defined in `packages/@sanime/domain/types.ts` alongside `OnboardingSession` (not `types/index.ts` — that file only has a comment pointing to the new location now, no re-export).
  - `OnboardingEvent` — the event union: the original (`WEITER`, `ZURUECK`, `AGB_AKZEPTIERT`, `REZEPT_OCR_ABGESCHLOSSEN`, `FELD_KORRIGIERT`, `SUPPLY_AUSGEWAEHLT`, `KONTAKT_ERFASST`, `OTP_VERIFIZIERT`, `ZAHLUNG_ERFOLGREICH`/`AUFTRAG_EINGEREICHT` (server-only), …) plus the Katalog/Krankheitsbild pairs added for the two extra entry paths: `KATALOG_PRODUKT_VORGEMERKT`/`KATALOG_PRODUKT_SELBSTZAHLER_GEWAEHLT`/`ZURUECK_KATALOG` and `KRANKHEITSBILD_STARTEN`/`KRANKHEITSBILD_AUSGEWAEHLT`/`KRANKHEITSBILD_PRODUKT_VORGEMERKT`/`KRANKHEITSBILD_PRODUKT_SELBSTZAHLER_GEWAEHLT`/`ZURUECK_KRANKHEITSBILD`.
  - `TRANSITIONS` — the actual state machine: an array of `{ from, event, to, guard? }` rows. **Every legal navigation edge, forward and backward, is an explicit row** — there is no implicit "any state can go back one step" rule and no generic fallback. If a screen dispatches an event with no matching `(from, event)` row, `transition()` returns `{ ok: false }` and nothing happens (client-side) or the backend throws a 400 (server-side) — same function, same rows, both places. When adding a new screen/step, you must add its rows here, including the `ZURUECK` row — forgetting it means the guard hook will bounce the user right back the moment they try to navigate away (this exact bug shipped twice during initial build, on the Rezept- and Krankenkasse-camera screens, before the rows were added). **`createWorkflow`'s `transition()` (`workflow.ts`) picks only the *first* rule matching `(from, event.type)`, never falls through to a second** — this is why the Katalog/Krankheitsbild self-pay branches each need their own distinct event name (`..._SELBSTZAHLER_GEWAEHLT`, `ZURUECK_KATALOG`/`ZURUECK_KRANKHEITSBILD`) rather than reusing `SUPPLY_AUSGEWAEHLT`/`ZURUECK` with a different guard: two rows for the same `(from, event)` pair can never both apply, so a fork in behavior must be a fork in event name.
  - `transition(session, event)` — the reducer; validates the row exists, checks its `guard` (e.g. required-fields-present before advancing), then applies `applyEventData` (a plain `switch` merging the event's payload into the relevant session fields) and returns the new session with `status` updated.
  - `hatPflichtfelderRezept` / `hatPflichtfelderKomplett` — exported guard predicates, reused by `review.tsx`/`datenpruefung.tsx` (to drive the "Weiter" button's disabled state) for the Rezept path specifically. `hatPflichtfelderKomplett` is **not** the completion guard anymore — `istAbschlussfaehig(session)` wraps it: `true` immediately if `session.selectedSupply` has no `hilfsmittelNr` (a self-pay pick never had a Rezept/Krankenkasse chain to complete), otherwise falls through to `hatPflichtfelderKomplett`. Both `apps/backend`'s `OnboardingService.complete()` and the app call `istAbschlussfaehig`, so the UI signal and the actual guard can never drift apart in either direction.
  - `OnboardingSession` also carries `eintrittspfad: 'REZEPT' | 'KATALOG_SELBSTZAHLER' | 'KRANKHEITSBILD_SELBSTZAHLER'` (pure navigation bookkeeping — which `ZURUECK*` event a shared screen like `termin.tsx` must dispatch — **never** a business-rule guard input, that's `istAbschlussfaehig`'s job), `vorausgewaehltesProduktId` (a Katalog/Krankheitsbild HiMi pre-selection, purely a VERSORGUNGSAUSWAHL UX nicety), and `ausgewaehltesKrankheitsbildId` (which taxonomy id was picked, for admin visibility).
  - `erstelleLeereSession(id)` — the initial `OnboardingSession` factory (app-side only; the backend hydrates a domain session from its own normalized Postgres tables instead, see "Backend" below).
- **`store/onboardingStore.ts`** — the Zustand store:
  - `dispatch(event, code?)` is the single choke point every screen calls, and is **request-then-apply, never optimistic**: it runs the shared `transition()` first as a fast-fail legality pre-check only (never written to the store), then on success calls the real backend (`lib/api/onboarding.ts`'s `patch()`) and replaces `session` wholesale with the server's response — the server injects fields the client can't compute itself (server-recomputed `produkte`, `devCode`, consent `ipAdresse`). On any failure (guard rejection or network/backend error), nothing changes and the caller gets `{ ok: false, reason }`; screens funnel that into `zeigeDispatchFehler()` (`lib/onboardingNav.ts`). Persistence-after-every-step (AsyncStorage for most fields, `expo-secure-store` via `lib/secureStorage.ts` for OCR/contact data specifically) and analytics instrumentation (`emitAnalyticsForTransition`) are structural side effects of a *successful* `dispatch`, not something a screen author can forget to call.
  - `STATUS_META: Record<OnboardingStatus, { route, schritt }>` — the *one* table mapping machine status to an expo-router path and a step number. Every redirect reads this table; there is no other place a status maps to a route. `schritt`'s numbering is only self-consistent *within* the Rezept path (1–11) — screens shared across all three entry paths (`termin.tsx`/`zusammenfassung.tsx`/`checkout.tsx`) do **not** use it for their `StepCounter` display, since the same status has a different position/total on a 6- or 8-step self-pay path than on the 11-step Rezept path. Those three screens instead call `schrittInfo(session)` (also in `onboardingStore.ts`), which resolves `{ aktuell, gesamt }` from a per-`eintrittspfad` `SCHRITT_REIHENFOLGE` ordered-status list. The Krankheitsbild-exclusive screens (`krankheitsbild.tsx`/`krankheitsbild-empfehlung.tsx`) just hardcode their own position (3/8, 4/8) like the Rezept-exclusive screens already did.
  - `pendingEinstiegEvent` — client-only (never persisted), holds a Katalog/Krankheitsbild product-pick event chosen *before* AGB/Datenschutz consent exists for the current (always-fresh) session. Every `starten()` lands at `WILLKOMMEN`, and the `KATALOG_*`/`KRANKHEITSBILD_*` `TRANSITIONS` rows only fire from `LEISTUNGSUEBERSICHT` with consent granted — so `hooks/useProduktAuswahlDispatch.ts` and `app/einstieg/index.tsx`'s Krankheitsbild option stash the intended event here and route to Willkommen/Leistungsübersicht instead of dispatching immediately; `leistungsuebersicht.tsx`'s final "Weiter" tap dispatches this pending event (if set) instead of plain `WEITER` once both consents are ticked, and pushes to `STATUS_META[result.session.status].route` — **not** a hardcoded `/scan/rezept` — since the destination now varies by what was pending.
  - `starten()` — calls the real `POST /onboarding-sessions`, stores the returned `sessionSecret` as the bearer token via `authStore.setToken()`, then hydrates from `GET .../current`; resumes an existing unfinished local session instead if one's already in memory (called from `app/onboarding/index.tsx`'s own CTA, from `app/einstieg/index.tsx`'s options, and from `hooks/useProduktAuswahlDispatch.ts` for a Katalog/Krankheitsbild pick).
  - `dispatch()` takes a `ClientOnboardingEvent` (`@sanime/domain`), which type-level excludes the two completion events (`SERVER_EVENT_TYPES`: `ZAHLUNG_ERFOLGREICH`, `AUFTRAG_EINGEREICHT`) — completion is never a PATCH. `einreichen()` is the client's only completion action: it calls `POST .../complete` for a Versorgung with no payment due at checkout (see "Checkout: wann wird bezahlt?" below); a paid self-pay purchase is completed only by the Stripe webhook.
  - `abschliessen()` — called only after the session is server-side `ABGESCHLOSSEN` (after `einreichen()` succeeded, or after `checkout.tsx`'s polling saw the webhook complete it), which is also why the `checkout_completed`/`onboarding_completed` analytics fire from here, not from `dispatch()`: derives a display-only `benutzer` client-side from the session's OCR/contact data if one doesn't exist yet (`benutzer.id` is never used by any backend ownership check — those key off the bearer secret), then clears the local session. **A `Supply` record does not exist before server-side completion succeeds** — matches the product rule that the binding order is only created after checkout succeeds.
- **`hooks/useOnboardingGuard.ts`** — called by every onboarding/scan screen with its own expected `OnboardingStatus` (or an array, e.g. `checkout.tsx` accepts `['CHECKOUT', 'CHECKOUT_FEHLGESCHLAGEN']`). On mismatch it `router.replace()`s to `STATUS_META[session.status].route`. This is what makes wrong-screen navigation — deep links, swipe-back, app relaunch mid-flow after a crash — structurally impossible instead of incidentally correct. Screens render `<OnboardingLoadingView />` while `!ready`. Its `requireOcrResult` option only actually enforces the Rezept photo/OCR requirement when `session.eintrittspfad === 'REZEPT'` — a self-pay session (Katalog or Krankheitsbild) legitimately has `ocrResult: null` for its whole lifetime, so `zusammenfassung.tsx`/`checkout.tsx` can keep passing `requireOcrResult: true` unconditionally and let the guard itself decide whether it applies.

### Routing (`app/`)

- `app/_layout.tsx` — root `Stack`; awaits `useAuthStore().laden()` then `useOnboardingStore().laden()`, **sequentially, not `Promise.all`** — `onboardingLaden()` reads `authStore`'s bearer token to call `GET /onboarding-sessions/current`, so it's a real dependency, not just style. Declares route groups `onboarding`, `(app)`, `scan` (full-screen modal), `einstieg` (also full-screen modal — the entry chooser reachable from the dashboard's `+`), and `katalog` (a plain push stack, deliberately *not* a full-screen modal — browsing should feel like browsing, not like starting a committed process). There is no `auth` route group — see below.
- `app/index.tsx` — entry gate: splash, then if `!onboardingAbgeschlossen` — redirect to `STATUS_META[session.status].route` if an in-progress `OnboardingSession` exists (mid-flow resume after a crash/close), else `/onboarding`; else always `/(app)/dashboard`, regardless of `benutzer` — there is no forced-login gate. A `benutzer === null` visitor (never onboarded, or logged out via Einstellungen) lands on the dashboard's guest empty state; identity is only re-established later, if at all, via a Krankenkassenkarte scan matched against the real backend (`lib/api/auth.ts`'s `matchByInsuredNumber()` → `POST /customers/match`, see `app/scan/krankenkasse.tsx`'s `pruefeArchivTreffer`). A hit **claims the current session** server-side rather than issuing a new token or short-circuiting to the dashboard — the in-progress order continues normally, since the customer may be starting a *new* Versorgung, not resuming a finished one. There is intentionally no manual "log back in" screen — `app/auth/otp.tsx` was deleted because the archive-match scan is now the single identity-recovery path; don't recreate an OTP re-login screen without first checking whether that decision has changed.
- `app/onboarding/` — `index.tsx` (Willkommen; no store reads except calling `starten()`+`dispatch(WEITER)` on its own CTA) → `leistungsuebersicht.tsx` (Leistungsübersicht: **one** machine status with 3 *local* substeps — process visual, reassurance animation, AGB/Datenschutz consent — the substep counter is component `useState`, not machine state, since only the consent checkboxes carry real data; those dispatch `AGB_AKZEPTIERT`/`DATENSCHUTZ_AKZEPTIERT` immediately per tap, "Weiter" is gated on both being accepted) → `agb.tsx` / `datenschutz-text.tsx` (static legal-text screens, reachable any time via links, not part of the state machine).
- `app/(app)/` — reachable by guests and logged-in users alike (see `app/index.tsx` above); bottom tabs (`dashboard`, `einstellungen`) — note the custom `PremiumTabBar` in `_layout.tsx` requires `Tabs.Screen` names to match the *exact* file-based route key (`dashboard/index`, not `dashboard/index.tsx`'s folder name `dashboard`) or the title/icon silently never attach and the raw route name leaks into the tab label; `options.href: null` (used to keep `dashboard/[id]` out of the tab bar) only works with expo-router's default tab bar, so the custom bar filters visible tabs itself via an explicit route-name allow-list. Both tab screens render a distinct guest-appropriate empty state when `benutzer` is `null` rather than falling back to placeholder identity data — match that pattern in any new `(app)` screen. The tab bar's floating center `CameraButton` now just pushes `/einstieg` (the entry chooser) instead of directly starting a Rezept session — see the dedicated section below for what that opens into. The dashboard's own empty-state CTA still does the direct one-tap `starten()` + push `/scan/rezept` shortcut (muscle memory for the common case), with a de-emphasized "Ohne Rezept? Katalog durchsuchen" link beneath it. Every new Versorgung re-collects AGB/Datenschutz consent via the onboarding machine (starts at `WILLKOMMEN`), including for repeat orders and regardless of entry path; this is a deliberate choice, not a bug, so don't "optimize" it into skipping straight to the camera/picker without checking first.
- `app/scan/` — the full "start a Versorgung" flow, **reused for both first-time onboarding and repeat orders** (hence living under `scan/`, not `onboarding/`): `rezept` → `review` → `krankenkasse` → `datenpruefung` → `versorgungen` → `termin` → `zusammenfassung` → `checkout`, plus `krankheitsbild` → `krankheitsbild-empfehlung` (see the dedicated section below) which feed into `termin`/rejoin `rezept` depending on the picked product. Every screen calls `useOnboardingGuard(status)` first, and `app/scan/_layout.tsx`'s `Stack` needs an explicit `<Stack.Screen name="...">` entry for every file in the folder (options like `gestureEnabled: false` are per-screen, but a missing entry is also just a silently-default-configured screen, not a broken one — still worth adding one for every new file to match this file's existing convention). OCR is real, on-device (`lib/ocr/`, see below) and split across the two capture screens (prescription fields on `rezept.tsx`, insurance fields on `krankenkasse.tsx`) rather than one combined call, so `session.ocrResult` is progressively filled in; the product catalog `erkenneKrankenkasse()` used to return alongside it is now always `[]` client-side, since the backend recomputes+discards it regardless (`termin.tsx` similarly fetches real appointment slots from `GET .../appointment-slots` rather than generating them locally). `checkout.tsx` skips the phone/OTP substep entirely and jumps straight to payment if `authStore.benutzer` already exists (the repeat-order case, including one just recognized via the Krankenkassenkarte archive match) — see `hooks/useOtpVerification.ts` for the shared send/verify mechanics (its `codeSenden`/`codeVerifizieren` **are** the `dispatch()` calls for `KONTAKT_ERFASST`/`OTP_VERIFIZIERT`; `checkout.tsx` must not additionally dispatch those events itself, or one tap fires two PATCH requests), now used only by `checkout.tsx`. Its final `abschluss` substep forks on `zahlungBeimCheckoutFaellig(session)`: a Rezept-Versorgung gets a "Verbindlich absenden" button (`einreichen()`, no payment, with a note that the Zuzahlung is billed after approval), a paid self-pay purchase gets the payment step. The payment step (`handleZahlung`) is a real Stripe integration (`@stripe/stripe-react-native`'s PaymentSheet) — see "Payments (Stripe)" below for the full picture, but the one thing to know before touching this screen: **`handleZahlung` never completes the session itself.** `presentPaymentSheet()` succeeding only means Stripe accepted the payment method: it polls the backend (`wartenAufAbschluss`) until the backend's own webhook has actually completed the session server-side. Don't "simplify" this back to an optimistic client-side dispatch — that would let a client claim a Versorgung it never paid for.
- `app/einstieg/` — the dashboard `+`'s entry chooser (`Rezept scannen` / `Krankheitsbild beschreiben` / `Katalog durchsuchen`), not part of the onboarding machine itself (no `useOnboardingGuard`) — see the dedicated section below.
- `app/katalog/` — the standalone catalog-browse screen, reachable from the dashboard, from `/einstieg`, and from `krankheitsbild-empfehlung.tsx`'s "vollen Katalog ansehen" fallback. Browsing itself never calls `starten()` — no session exists until a product is actually picked. See the dedicated section below.

### State (`store/`)

Three independent Zustand stores; `onboardingStore` is allowed to call into `authStore` one-directionally (from `abschliessen()`), but not the reverse — `authStore` has no awareness of onboarding:
- `authStore.ts` — `benutzer`/`token`/`onboardingAbgeschlossen`, persisted to AsyncStorage under `sanime_*` keys, hydrated via `laden()` on app boot. `token` is the real current onboarding session's `sessionSecret` (set via `setToken()` the moment a session exists, before any `benutzer` is known) — not a fabricated login credential, and never conflated with "is this a known customer."
- `onboardingStore.ts` — see "State machine" above.
- `versorgungStore.ts` — order/supply history (`Versorgung[]`), loaded via `lib/api/supply.ts`'s `list()` and mapped through `lib/supplyMapper.ts`'s `mapSupplyRowToVersorgung()` (translates the backend's 14-status `SupplyStatus` to the app's 9-status `OrderStatus` — no backend status maps to `CANCELLED` today, that's simply unreachable from real data, not a mapping bug). A 403 (an unclaimed session has no customer to own a history) is mapped to an empty list in `laden()`, not surfaced as an error.
- `scanStore.ts` **has been deleted** — its fields (photo URIs, OCR result/confidence, selected product) now live on `OnboardingSession`. If you find a reference to it, it's stale.

**Types**: `types/index.ts` still owns app-only domain types — `OrderStatus`, `Versorgung`/`TimelineEvent`/`OffeneAktion`, `Benutzer` — but `OnboardingStatus`, `OnboardingSession`, `Einwilligung`/`OnboardingConsent`, `TerminSlot`, `CustomerContact`, `Produkt`, and the OCR result/confidence shapes moved to `packages/@sanime/domain/types.ts` once the backend needed to share them (`types/index.ts` has a comment pointing there — don't redeclare them locally). Extend the domain package for anything the backend also needs to know about; keep purely app-display types (`Versorgung`, `OrderStatus`, etc.) in `types/index.ts`. The transition table/reducer logic itself belongs in `packages/@sanime/domain/onboarding.ts`, not either types file. `Produkt.hilfsmittelNr` is `string | undefined`, not required — a falsy value is exactly what marks a product as self-pay throughout the FSM (`istAbschlussfaehig`, the two `*_SELBSTZAHLER_GEWAEHLT`/`*_VORGEMERKT` event pairs); `packages/@sanime/domain/krankheitsbild.ts` additionally exports `Krankheitsbild`, the static placeholder condition taxonomy (`KRANKHEITSBILD_KATALOG`), `findeKrankheitsbild(id)`, and `matcheKrankheitsbild(transcript)` (the on-device voice matcher) — see the dedicated section below.

Transcript and audio stay in React state only — never `AsyncStorage`/`SecureStore`, never sent anywhere — mirroring OCR's "the source data never leaves the device" rule; only the final resolved `krankheitsbildId` (via `@sanime/domain`'s `matcheKrankheitsbild`) is ever dispatched, and only after the user explicitly confirms a "Meintest du: X?" banner — never auto-dispatched. `start()` passes `requiresOnDeviceRecognition: true`, which **fails loudly** (an `error` event, surfaced as a concrete-next-step German message) if the device can't do on-device recognition, rather than silently falling back to network-based recognition — that fallback would violate the on-device-only guarantee. The native module needs `app.json`'s `expo-speech-recognition` plugin entry (already wired, injects `NSMicrophoneUsageDescription`/`NSSpeechRecognitionUsageDescription`/`RECORD_AUDIO`) and a dev-client rebuild to actually work on device — plain `expo start` / Expo Go can't load it.
- `ocr/` — real, on-device OCR (`erkenneRezept()`/`erkenneKrankenkasse()`, plus `detector.ts`, `processor.ts`, `engine.ts`, `rezeptParser.ts`, `egkParser.ts`, `validatoren.ts`, `mapper.ts`), wired into `app/scan/rezept.tsx`/`krankenkasse.tsx`. Runs entirely on-device via `expo-text-extractor`; throws `FalschesDokumentError` when the photographed document doesn't match the expected type. `processor.ts`'s `normalisiereBild()` deliberately does *not* do perspective correction/denoise/contrast for v1 (EXIF-rotation-baking + downscale only) — see `work/Ocrintegration.md` before treating that as a bug to fix. **The original Rezept/eGK photo never leaves the device** — only the OCR-extracted fields are sent to the backend (DSGVO data minimization); `event.uri` in the dispatched onboarding events stays a purely local sandbox path the server never dereferences, and `onboarding.service.ts`'s `*DocumentId` columns stay hardcoded `null` deliberately.
- `supplyMapper.ts` — `mapSupplyRowToVersorgung()`, the one place the backend's `SupplyStatus`/row shape gets translated into the app's `Versorgung`/`OrderStatus` — see "State (`store/`)" above.
- `terminplanung.ts` — `terminAusVorschlag(slot, index)` maps the real `GET .../appointment-slots` response (`{supplierId, productId, start, end}`, no id/address) into the app's `TerminSlot` shape, marking the first (chronologically earliest) slot as "Schnellster Termin". `terminAusKalenderdatum()` is untouched, pure client-side date formatting for the manual-calendar fallback — no backend call, nothing for the server to be authoritative about.
- `mockOcr.ts` / `mockKundenArchiv.ts` **have been deleted** — the product catalog and archive-match are both real backend calls now (`lib/api/catalog.ts`, `lib/api/auth.ts`'s `matchByInsuredNumber()`). If you find a reference to either, it's stale.
- `analytics.ts` — `trackOnboarding(event)` takes a **closed discriminated union** (`OnboardingAnalyticsEvent`) with no payload slot capable of carrying OCR values, names, or diagnoses — health data is structurally unrepresentable in an event, not merely filtered at runtime. Events fire centrally from `onboardingStore.dispatch()`'s internal mapping, not from individual screens (guarantees exactly one event per real transition, and keeps the entire "no health data in analytics" surface auditable in one file).

**`constants/legal.ts`**: `AGB_VERSION`/`DATENSCHUTZ_VERSION` string constants (bump on text changes — this is the audit trail until a backend/CMS exists) plus the placeholder legal text shown on `agb.tsx`/`datenschutz-text.tsx`.

**Labels (`constants/labels.ts`)**: German user-facing copy for `OrderStatus` (label + description) plus `StatusSteps`, the canonical ordered subset of statuses used to render timelines. Status display strings belong here, not inline in components.

**Design system (`packages/@sanime/design-system`)**: an internal monorepo package — `colors.ts`, `spacing.ts`, `radius.ts`, `blur.ts`, `glass.ts`, `opacity.ts`, `shadows.ts`, `typography.ts`, `durations.ts`, `springs.ts`, `haptics.ts`, `elevation.ts` — aggregated via its `index.ts` into a `D` object (colors, spacing, radii, typography, spring presets) plus named exports like `durations`. Import as `@sanime/design-system`. Every onboarding/scan screen and every `components/onboarding/*`/`components/ui/*` component uses this exclusively now — there is no second/older token system to avoid.

**Components (`components/`)**: `components/ui/` holds generic building blocks (Button, Card, GlassCard, CameraButton, StatusBadge, CircularProgress, ProcessStep, SectionHeader, `Checkbox`, `FormField`, and now `EinstiegOption` — the large tappable card used by `/einstieg` — and `MicButton`, the voice-input trigger); `components/onboarding/` holds onboarding/scan-specific composites (`DatenFeld` — the editable OCR-field-with-confidence-dot, shared by `review.tsx`/`datenpruefung.tsx`; `StepCounter`; `MiniKalender`; `OnboardingLoadingView`, the guard's loading fallback); `components/produkt/ProduktKarte.tsx` — the product display card, extracted from `versorgungen.tsx` (which was its only user pre-Katalog) so `app/katalog/` and `app/scan/krankheitsbild-empfehlung.tsx` can share it; renders no HiMi-Nr. row (and a "Selbstzahler-Artikel" badge instead) when `produkt.hilfsmittelNr` is falsy; `components/dashboard/` holds dashboard-specific composites (StatusTimeline, VersorgungCard). Business logic belongs in stores/screens, not in these UI components.

## Backend (`apps/backend/`)

An npm-workspaces monorepo member (root `package.json`'s `workspaces`), NestJS + Postgres/Drizzle, sharing `packages/@sanime/domain/` (the onboarding/supply/deletion-request FSMs, plain TypeScript, no NestJS import) and `packages/@sanime/design-system` (app-only, backend never imports it) with the mobile app. Neither `@sanime/domain` nor `@sanime/design-system` has a build step — `package.json`'s `main`/`types` point straight at raw `.ts` source, which is why the backend must run via `ts-node` (see the Commands section's gotcha) and why Metro resolves the app's imports of them without any special config.

**Modules** (`src/modules/`, one directory each, NestJS `@Module`-per-folder): `auth` (admin JWT + `CustomerSessionAuthGuard`, which hashes a bearer secret and looks up an `onboarding_sessions` row — there is no customer password/login, "auth" here means "which session/admin is this request"), `onboarding` (the integration module — hydrates/dehydrates the full domain `OnboardingSession` from ~7 normalized tables, the only module allowed to call `transition()` against a real request), `customer` (Krankenkassenkarte archive-match, `/customers/match`), `catalog` (products/suppliers/manufacturers/categories — see the dedicated section below for `GET /products`'s real category/text filtering and the Krankheitsbild lookup added alongside the app feature of the same name; `catalog.mapper.ts`'s `toProdukt()` lives here, not in `onboarding/`, since `CatalogController`'s own endpoints need it directly and `onboarding` already depends on `catalog`, not the reverse), `document` (S3/MinIO presigned uploads — unused by the OCR flow specifically, see the DSGVO note above), `health-data` (OCR results + insurance policies, no controller, consumed internally only), `supply-order` (`SupplyOrderService.applyTransition()` is the single choke point for every order status change, replaying `@sanime/domain/supply.ts`'s FSM), `appointment` (`SupplierCalendarService.proposeSlots()` — real capacity-aware slot search, counts confirmed bookings only, degrades gracefully instead of throwing when a supplier is saturated), `admin` (inbox/order-management for staff), `notification` (`NotificationProvider` port, logs in dev/throws in production — never fakes delivery), `job-queue` (`InProcessJobQueue`, in-memory now but ported to swap for BullMQ later without an interface change), `verification` (OTP: `DevCodeVerificationProvider` returns the code in dev, throws in production), `consents`, `audit` (`audit_entries`/`access_logs`, `@AuditRead()` decorator), `data-export`/`deletion-requests`/`retention` (GDPR: async export bundles, pseudonymize-not-hard-delete customer erasure that retains billing/audit rows, scheduled retention enforcement), `payment` (Stripe — see "Payments (Stripe)" below), `organizations`/`idempotency`/`health` (infra: multi-tenancy, the `Idempotency-Key` middleware, the health-check endpoint).

**Multi-tenancy & ownership**: every repository extends `TenantScopedRepository` and filters by `organizationId` (`DEFAULT_TENANT_CONTEXT` today, since there's one pilot tenant — the seam exists, not yet exercised with a second org). Customer-scoped routes (supplies, orders, data-export, deletion-requests) use `resolveOwnerFilter(principal)`: an admin principal gets `null` (unrestricted), a customer principal with a real `customerId` gets scoped to it, and — critically — an **unclaimed** customer session (`customerId === null`, i.e. never archive-matched) **fails closed with a 403**, never falls through to "unrestricted." Don't reorder that logic; it was a live cross-customer data leak once, fixed in Layer 4.

**Observability** (`src/common/tracing/`, `src/common/metrics/`): both are opt-in, no-op by default (exactly like the existing `SENTRY_DSN` block in `main.ts`) — set `OTEL_EXPORTER_OTLP_ENDPOINT` for real trace export, `METRICS_ENABLED=true` (+ optional `METRICS_PORT`, default 9464) for a live Prometheus `/metrics` endpoint. `tracer.ts`'s `withSpan()` correctly handles async functions (ends the span only once the awaited work settles, not the instant the promise is created — a real bug, fixed). `metrics.ts` exports `record*(...)` functions rather than raw `Counter`/`Histogram` objects **on purpose**: unlike `trace.getTracer()`, `metrics.getMeter()` is not a dynamic proxy — an instrument created before `initMetrics()` registers a real `MeterProvider` stays permanently bound to the no-op meter, so instrument creation must be lazy (first-real-call), not module-load-time. Don't "simplify" this back to exported instrument objects; it silently breaks metrics collection with no error anywhere.

For anything not covered here — exact endpoint list, DTO/zod schemas, migration history — read `apps/backend/src/modules/<name>/` directly rather than assuming this section is exhaustive; it's a map, not the territory.

## Katalog-Browsing, Krankheitsbild-Erfassung & Sprach-Eingabe

Three ways to reach the same downstream flow (Termin/Zusammenfassung/Checkout, and — for Hilfsmittelnummer picks — the Rezept-Prüfung/Datenprüfung chain): scan a Rezept (original), pick straight from the catalog, or describe a Krankheitsbild (by search or by voice) and pick from a recommendation. All three share one rule: **a client never gets to decide whether a product is HiMi (insurance) or self-pay** — the backend re-fetches the real product and 400s if the client dispatched the wrong branch event for it (`KATALOG_PRODUKT_VORGEMERKT` requires a HiMi product, `KATALOG_PRODUKT_SELBSTZAHLER_GEWAEHLT` requires none — same for the `KRANKHEITSBILD_*` pair).

**Katalog (`app/katalog/`, `lib/api/catalog.ts`, `apps/backend/src/modules/catalog/`)**: `GET /products` now takes optional `categoryId`/`q` query params (`ProductsRepository.listActive`'s `and(...)` conditions), and both `GET /products` and `GET /products/:id` return the mapped `Produkt` shape (`catalog.mapper.ts`'s `toProdukt`), not the raw joined repository row — that mapping used to only happen internally in `onboarding.service.ts`; the two endpoints were dead code before this feature activated them for real. `GET /catalog/categories`, `GET /products` and `GET /products/:id` are **public** (no guard; the app calls them with `auth: false`) precisely because browsing happens before any session/bearer token exists — they expose catalog data only, categories trimmed to `{id, name}`; `GET /suppliers` stays admin-only. `app/katalog/index.tsx` never calls `starten()` on mount — only picking a product does, via `hooks/useProduktAuswahlDispatch.ts` (shared with `krankheitsbild-empfehlung.tsx` via its `herkunft: 'katalog' | 'krankheitsbild'` parameter, which only changes which event pair gets dispatched).

**Krankheitsbild (`app/scan/krankheitsbild.tsx` + `krankheitsbild-empfehlung.tsx`, `packages/@sanime/domain/krankheitsbild.ts`, `apps/backend/src/modules/catalog/categories.repository.ts`'s `findByKrankheitsbildId`)**: `catalog_categories.krankheitsbild_id` (nullable) tags a category with one of the static taxonomy's ids — deliberately **not** a foreign key to its own table, since the taxonomy is static domain data shared by both runtimes via `@sanime/domain`, not a database entity. `CatalogService.listProductsForKrankheitsbild()` resolves the id → tagged categories → active products in them, returning `[]` (not "everything") when nothing is tagged yet — matches the placeholder-seed-data stage, don't "fix" it into a fallback. `OnboardingService.patchInner()`'s `KRANKHEITSBILD_AUSGEWAEHLT` branch always recomputes `produkte` server-side from `krankheitsbildId`, same "never trust the client's recommendation list" discipline as the Rezept path's `KRANKENKASSE_OCR_ABGESCHLOSSEN`.

**Voice (Phase 3, `lib/voice/krankheitsbildSpracherkennung.ts`, `components/ui/MicButton.tsx`)**: on-device only (`expo-speech-recognition`'s `requiresOnDeviceRecognition: true`) — transcript/audio never leave React state, only the final confirmed `krankheitsbildId` is ever dispatched, and only after the user taps "Ja, das ist es" on a confirmation banner (never auto-dispatched on a recognized match — same "derived output is never final" rule OCR follows). `matcheKrankheitsbild()` (in the domain package, not app-only, so it can't drift from the taxonomy it searches) is a plain keyword/synonym substring match — no cloud NLP/LLM call, by design. Needs a dev-client rebuild (`npx expo prebuild`/`run:ios`/`run:android`) to actually work — the native module isn't in Expo Go and wasn't rebuilt into this repo's own dev client as part of adding it; `app.json`'s `expo-speech-recognition` plugin entry (verified via `npx expo config --type public`, without a full rebuild) already injects the iOS/Android permission strings.

**FSM mechanics worth internalizing before touching any of this**: `createWorkflow`'s `transition()` (`packages/@sanime/domain/workflow.ts`) matches only the *first* `TransitionRule` for a given `(from, event.type)` — there's no second-row fallback, so every behavioral fork (HiMi vs. self-pay; which screen a "back" tap lands on) had to become a distinct event (`ZURUECK_KATALOG`/`ZURUECK_KRANKHEITSBILD` vs. plain `ZURUECK`), not a shared event with a different guard. `store/onboardingStore.ts`'s `schrittInfo()` and the `pendingEinstiegEvent` mechanism (see "State machine" above) exist specifically because these two new paths broke assumptions ("the step counter total is always 11", "a session always dispatches plain `WEITER` from Leistungsübersicht") that held for the single-path Rezept flow.

## Payments (Stripe)

`checkout.tsx`'s Zuzahlung (co-pay) charge is a real Stripe integration, not a mock — `@stripe/stripe-react-native`'s `PaymentSheet` on the app side, `apps/backend/src/modules/payment/` on the backend. Both are opt-in like every other production-only integration in this repo (Sentry, tracing, metrics): unset `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` means the backend still boots and every other feature works fine, only the payment endpoints themselves fail loudly (a real Stripe authentication error, not a silent no-op) the moment someone actually tries to use them.

**Checkout: wann wird bezahlt?** `@sanime/domain`'s `zahlungBeimCheckoutFaellig(session)` decides it: only a self-pay product (no `hilfsmittelNr`) with `eigenanteil > 0` is paid at checkout — that's an ordinary purchase. A Rezept/GKV-Versorgung is **never** paid at checkout: the statutory Zuzahlung is collected by the Leistungserbringer later (§ 43c SGB V), after Krankenkassen-Genehmigung/delivery, since its amount isn't reliably known at order time (Befreiung § 62 SGB V, under-18s, contract prices). The FSM enforces this with two distinct `CHECKOUT → ABGESCHLOSSEN` events — `AUFTRAG_EINGEREICHT` (guard: no payment due; reached via `POST .../complete` → `OnboardingService.einreichen()`) and `ZAHLUNG_ERFOLGREICH` (guard: payment due; reached only via the webhook → `OnboardingService.abschliessenNachZahlung()`) — so `/complete` can never finish a paid purchase and `POST .../payment-intent` 400s for a Rezept-Versorgung. Both go through the private `abschliessen()`, which runs the FSM check *before* creating the Supply. `customerCopaySnapshotCents` on the Supply is the basis for collecting the Zuzahlung later; that later collection (invoice/SEPA, payment provider choice) is **not built yet**.

**The one rule that matters more than any other here: the mobile app never declares a payment successful.** `handleZahlung` in `checkout.tsx` creates a PaymentIntent (`POST /onboarding-sessions/:id/payment-intent`, amount computed server-side from the session's selected product — never trusted from the client) and shows Stripe's PaymentSheet. A successful `presentPaymentSheet()` only means the customer's payment method was accepted by Stripe — it does **not** complete the Versorgung. Completion (`OnboardingService.abschliessenNachZahlung()`) is called exclusively from `StripeWebhookController` (`POST /webhooks/stripe`), reacting to a `payment_intent.succeeded` event whose signature has been verified against `STRIPE_WEBHOOK_SECRET`. The app just polls (`wartenAufAbschluss`, ~10 tries × 1.2s) until the session's own status flips to `ABGESCHLOSSEN`. Don't "simplify" this into the client calling `POST .../complete` right after `presentPaymentSheet()` succeeds — that would let a client complete an order it never actually paid for, since nothing server-side would have independently verified the charge.

**Module layout** (`apps/backend/src/modules/payment/`): `PaymentsRepository` (the `payments` table — one row per Stripe PaymentIntent, `status` mirrors Stripe's own PaymentIntent.status values directly), `PaymentService` (Stripe client injected via a `STRIPE_CLIENT` factory provider — not `new Stripe(...)` inline — purely so tests can substitute a mock without real credentials or network access), `PaymentModule` (exports only `PaymentService`, imports nothing from Onboarding — same one-directional pattern as `AppointmentModule`). The webhook controller itself (`StripeWebhookController`) deliberately lives in `onboarding/controllers/`, not in `PaymentModule` — it needs `OnboardingService.abschliessenNachZahlung()`, and `PaymentModule` must never import `OnboardingModule` back (would create the exact cycle `OnboardingModule → PaymentModule → OnboardingModule`).

**Idempotency**: Stripe delivers webhooks at-least-once. `PaymentService.markSucceeded()` checks the payment row's current status before acting — a retried `payment_intent.succeeded` for an already-completed payment is a no-op, not a second completion call (which would hit an illegal FSM transition and throw). `PaymentService.createOrReuseIntent()` similarly reuses an existing reusable-state PaymentIntent for a session rather than creating a second live one — a customer backgrounding the app mid-payment and reopening it must never risk being charged twice.

**Two real bugs found while building this, both from assuming a library behaves like a sibling library**:
1. Stripe's Node SDK throws immediately at `new Stripe(apiKey)` if `apiKey` is falsy ("Neither apiKey nor config.authenticator provided") — it does **not** defer that check to the first real API call. The "unset key = no-op until used" pattern that works for Sentry/tracing/metrics doesn't work here unmodified; `PaymentModule`'s factory falls back to an obviously-fake placeholder string (`'sk_test_not_configured'`) so construction always succeeds, and an actual API call with it fails with Stripe's own real (and correctly logged) authentication error instead.
2. `NestFactory.create(AppModule, { rawBody: true })` is required in `main.ts` for `StripeWebhookController`'s `@RawBody()` to have anything to read — Stripe's HMAC signature is computed over the exact original request bytes, and Nest's default JSON body parsing (which still runs for every other route, `rawBody: true` doesn't disable it) would re-serialize the body and break verification. e2e tests exercising the webhook need the same option on `moduleRef.createNestApplication({ rawBody: true })`.

**Local/dev setup**: `apps/backend/.env` needs `STRIPE_SECRET_KEY` (a real `sk_test_...` from your own Stripe Dashboard — no code change to go live later, only swapping for `sk_live_...`) and `STRIPE_WEBHOOK_SECRET`. For local webhook delivery, run `stripe listen --forward-to localhost:3000/api/v1/webhooks/stripe` (Stripe CLI) and use the secret it prints. The app needs `app.json`'s `expo.extra.stripePublishableKey` (or `EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY`) set to the matching `pk_test_...` — safe to commit/ship client-side, unlike the secret key. **None of this repo's own testing exercises real Stripe API calls** — `payment.service.spec.ts` and `test/payment.e2e-spec.ts` both inject a mocked Stripe client for `paymentIntents.create`/`retrieve`, and verify webhook signatures for real (pure local HMAC, no network) against a throwaway `Stripe` instance. Real end-to-end verification (an actual card charge in Stripe's test mode) has not been done and needs a real Stripe test-mode account.

**Apple/Google Pay**: not enabled in this pass (card only) — `app.json`'s `@stripe/stripe-react-native` plugin entry has no `merchantIdentifier`, which only gates the *optional* Apple Pay entitlement (the plugin's other iOS step, adding a blank Swift file so the native module builds at all, is unconditional and always needed — don't remove the plugin entry entirely even if Apple Pay stays off). Adding Apple Pay later needs a registered Apple Merchant ID plus `merchantIdentifier` in the plugin config; Google Pay needs `enableGooglePay: true`. Server-side, `automatic_payment_methods: { enabled: true }` is already set unconditionally in `PaymentService.createOrReuseIntent` — it's safe regardless, Stripe only actually offers a payment method the client is configured to present.

## Manual/interactive testing

There's no automated UI test runner, and this is a native app — `npm run typecheck`/`lint` catch static errors but not navigation/state bugs (several real bugs, including one that made a screen's confirmation checkbox completely unreachable, were only caught by actually tapping through the app). For interactive verification, drive a real iOS Simulator with **`idb`** (Meta's iOS Development Bridge) rather than guessing from screenshots alone.

**One-time setup:**
```bash
brew tap facebook/fb
brew trust --formula facebook/fb/idb-companion   # required: idb-companion is an untrusted (non-default) tap
brew install idb-companion
brew install pipx
brew install python@3.11   # fb-idb's asyncio usage is incompatible with newer Python (3.12+); pin 3.11
pipx install fb-idb --python /opt/homebrew/opt/python@3.11/bin/python3.11
```
`npx expo start --ios` will try to auto-install Expo Go and typically fails in a sandboxed/no-App-Store environment ("Fetching Expo Go" → `fetch failed`) — and Expo Go generally only supports one or two recent SDKs anyway, so for this repo's SDK version it may simply be unavailable. Use a real dev build instead: `npx expo run:ios` (builds native + installs on the simulator; first run takes several minutes for CocoaPods/Xcode build).

**Per-session:**
```bash
export PATH="$PATH:/Users/lemi/.local/bin"          # idb CLI lives here after pipx install
UDID=$(xcrun simctl list devices | grep Booted | grep -oE '[0-9A-F-]{36}')
idb_companion --udid $UDID &                         # one companion process per booted simulator
idb connect $UDID <port-from-companion-stdout>       # or just `idb list-targets` to confirm "Connected"
```
Then drive it:
```bash
idb ui describe-all --udid $UDID   # dumps the accessibility tree as JSON: every AXLabel + its {x,y,width,height} frame,
                                    # in POINT space (not pixels) — same space `ui tap` expects. This is the reliable
                                    # way to find what to tap; don't eyeball coordinates from a screenshot's pixel size.
idb ui tap <x> <y> --udid $UDID
idb ui text "some text" --udid $UDID   # types into whatever TextInput is currently focused
idb ui swipe <x1> <y1> <x2> <y2> --udid $UDID   # scroll; also in point space
xcrun simctl io $UDID screenshot /tmp/out.png   # screenshot is in PIXEL space — don't mix the two coordinate systems
```
A small helper for tap-by-accessibility-label (finds the element, taps its center) is worth writing once per session — see the pattern of `describe-all` piped through a short Python script filtering by `AXLabel`.

**Gotchas hit in practice:**
- Native system sheets (the photo picker, permission dialogs) are a separate process and don't appear in `describe-all` — estimate their coordinates from a screenshot instead (convert pixel→point by dividing by the device's scale factor, e.g. 1206px / 402pt = 3.0 on an iPhone 17 Pro).
- If the app stops responding to Fast Refresh (edits not showing up after a file save), the dev-client's live Metro connection has likely dropped — `xcrun simctl terminate $UDID <bundle-id> && xcrun simctl launch $UDID <bundle-id>` fetches a fresh bundle without clearing AsyncStorage/app state.
- A floating/overlapping element (e.g. two views occupying the same screen region) doesn't always deliver taps to whichever one is visually on top — if a tap keeps landing on the wrong element despite correct-looking coordinates, that's a real hit-testing ambiguity worth flagging, not just an automation mistake.
- After adding new route files, expo-router's typed-routes declaration (`.expo/types/router.d.ts`) is normally regenerated by the dev server on file-watch; if you're editing routes without a running `expo start`, it can go stale and cause spurious `tsc` errors on `router.push('/new/route')` calls — regenerate by starting the dev server once, or via `expo-router`'s `typed-routes/generate` module directly.
- `idb` can't simulate microphone input, so `krankheitsbild.tsx`'s `MicButton` (voice-to-Krankheitsbild matching) can only be exercised by hand on a real device or the Simulator's own mic passthrough — everything else on that screen (the search/picker, the confirmation banner's buttons) is still `idb`-drivable normally.
