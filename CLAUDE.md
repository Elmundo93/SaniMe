# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Product context

SaniMe is a mobile app (Expo/React Native) that digitizes the German "Hilfsmittelversorgung" process (medical supply procurement via prescription + statutory health insurance). The customer just photographs documents (Rezept, Krankenkassenkarte); OCR runs entirely on-device (`lib/ocr/`), and a NestJS/Postgres backend (`apps/backend/`) handles product matching, insurance submission, and order tracking. The app runs against this real backend end-to-end — nothing in `store/` is mocked anymore (the last mocks, `lib/mockOcr.ts` and `lib/mockKundenArchiv.ts`, were deleted once the backend cutover landed). See "Backend (`apps/backend/`)" below for that side; the rest of this file covers the mobile app.

Rezept-Scan is no longer the only way to get a Versorgung: the middle start tab **Entdecken** (and `/katalog`) is a sessionless catalog with search (+ on-device voice), „Wobei brauchst du Hilfe?“ (everyday Bedarfe **and** Krankheitsbilder in one discovery path) and a two-level category tree. Browsing never creates a session; „In den Warenkorb“ on a product detail page only adds the product to the **local, on-device Warenkorb** (`store/warenkorbStore.ts`), and only „Zur Kasse“ in the Warenkorb tab starts a process. One order (= one onboarding session) holds **several products** (`OnboardingSession.positionen`); every Kassenartikel carries **its own Rezept**, scanned at the Kasse. See "Katalog & Discovery" and `warenkorbStore` under "State (`store/`)" below.

Product/UX rules that should inform any feature work:
- One task and one primary CTA per screen; always allow Back/Forward with visible progress.
- Automate over form input — never ask the user for information that could be derived (OCR, defaults, recommendations).
- Every OCR/derived field must stay user-editable; OCR output is never final.
- Error messages must state a concrete next step for the user (German, e.g. "Wir konnten dein Rezept nicht vollständig erkennen. Bitte überprüfe die markierten Felder." — not "OCR Error").
- Health/insurance data (prescription photos, diagnoses, insurance IDs) is highest-sensitivity: never log it, send it to analytics, or store it unencrypted.
- New UI must meet WCAG 2.1 AA: 44×44 touch targets, screen reader labels, logical focus order, sufficient contrast, Dynamic Type support.
- The product catalog (`Produkt` type) is a placeholder during development — never hardcode real manufacturer/pricing/Hilfsmittelnummer data as if it were production data.
- A product with no Hilfsmittelnummer (`Produkt.hilfsmittelNr` is optional) is a self-pay ("Selbstzahler") item — it never needs a Rezept and is paid at checkout; a product *with* one is a Kassenartikel that needs its own complete Rezept before the order can be submitted — **or** the customer explicitly buys it without Rezept at our price (`Produkt.selbstzahlerPreis`, from `supplier_products.self_pay_price_cents`; `POSITION_OHNE_REZEPT`, confirmed by an Alert so nobody pays full price just because the Rezept isn't photographed yet). Then it is paid at checkout and submitted as a self-pay Supply (no HiMi-Nr./Rezept/Krankenkasse snapshot). Never the reverse: a self-pay product never goes to the Krankenkasse. Only the server decides which is which (it re-fetches every product from the catalog).
- Search terms, Bedarf/Krankheitsbild ids and catalog filters are potential health data: never log them, never put them (or product/category names) into analytics. Backend `scrub.ts` masks all query-string values for Sentry; the exception filter returns `request.path`, not `request.url`.

## Commands

**App** (run from the repo root):
```bash
npm run start       # expo start — Metro bundler, scan QR or press i/a for simulator
npm run ios         # expo run:ios — build & launch native iOS
npm run android     # expo run:android — build & launch native Android
npm run lint        # eslint .
npm run typecheck   # tsc --noEmit
npm run test        # jest (jest-expo preset) — currently only lib/ocr/*.test.ts and packages/@sanime/domain/*.test.ts (incl. onboarding.test.ts, krankheitsbild.test.ts, katalogSuche.test.ts)
```

`npm run lint` requires `.eslintrc.js` (extends `expo`) at the repo root — this file didn't exist before and lint silently failed with no config found; it's checked in now, don't delete it.

Jest is configured (`jest.config.js`, `jest-expo` preset) with a `test` script; run with `npm run test`. Tests are co-located next to source as `*.test.ts` — under `lib/ocr/` (parsers/validators/mapper) and `packages/@sanime/domain/` (the FSMs). No app-side integration/E2E/accessibility test automation exists — see "Manual/interactive testing" below for that.

Always run `npm run typecheck` and `npm run lint` after app changes; also run `npm run test` when touching `lib/ocr/` or `packages/@sanime/domain/`. For interactive verification (actually tapping through screens), see "Manual/interactive testing" below.

**Backend** (`apps/backend/`, proxied from the root via npm workspaces — run from the repo root, not `cd apps/backend`):
```bash
npm run backend:dev          # node --watch ts-node — NOT `nest start`/`nest build`, see the gotcha below
npm run backend:typecheck    # tsc --noEmit -p tsconfig.build.json
npm run backend:lint         # eslint "{src,test}/**/*.ts"
npm run backend:test         # jest — unit/integration, needs the docker-compose Postgres running
npm run backend:test:e2e     # jest --config ./test/jest-e2e.json
npm run backend:db:generate  # drizzle-kit generate — after any schema/*.ts change
npm run backend:db:migrate   # drizzle-kit migrate
npm run backend:db:seed      # organizations → admin → catalog → qa (Ratgeber) → customers → retention-policy seeds, in that order
```
`docker compose -f apps/backend/docker-compose.yml up -d` starts Postgres + MinIO (S3-compatible object storage for document uploads) before `backend:dev`/`backend:test*`. Copy `apps/backend/.env.example` to `apps/backend/.env` first (`DATABASE_URL`, `STORAGE_*`, `VERIFICATION_CODE_PEPPER`, `ADMIN_JWT_SECRET` — the last two must be real values, not the checked-in placeholders, outside local dev).

**Critical gotcha**: `apps/backend/src/main.ts` boots fine under `ts-jest`/`tsx` but a plain `nest build && node dist/main.js` (or `nest start`) crashes with `ERR_MODULE_NOT_FOUND` resolving `@sanime/domain/types` — `@sanime/domain` is deliberately raw, unbuilt TypeScript (same convention as `@sanime/design-system`), and plain Node's native TS/ESM handling can't follow its extensionless internal imports the way `ts-node`'s require hook can. `start`/`start:dev` are already wired to `ts-node` for this reason — don't "fix" them back to `nest start`/`nest build`.

Always run `npm run backend:typecheck` after backend changes; run `npm run backend:test`/`backend:test:e2e` when touching anything under `apps/backend/src/modules/` or `packages/@sanime/domain/` (the FSM the backend and app both import).

## Architecture

**Stack**: Expo (SDK 57) + expo-router (file-based routing, typed routes enabled) + React Native 0.86 + NativeWind (Tailwind for RN, see `tailwind.config.js`/`global.css`) + Zustand for state + AsyncStorage for persistence. Path alias `@/*` maps to repo root (`tsconfig.json`), though existing code consistently uses relative imports (`../../types`) instead — match that convention, not the alias.

The onboarding-to-checkout flow is implemented end-to-end as an explicit **state machine**, not a hardcoded screen chain, with two entry paths:
- **Warenkorb** (catalog): local cart → „Zur Kasse“ → (Willkommen → Leistungsübersicht/consent, only without durable consent) → `WARENKORB_UEBERNOMMEN` → **CHECKOUT**.
- **Rezept zuerst**: Willkommen → Leistungsübersicht/consent → Rezeptaufnahme → Rezeptprüfung → Krankenkassenkarte → Datenprüfung → Versorgungsauswahl (`SUPPLY_AUSGEWAEHLT` adds a position carrying that Rezept) → **CHECKOUT**.

**CHECKOUT is a hub**: Rezept scan for a position (`REZEPT_FUER_POSITION` → Rezeptaufnahme … Datenprüfung → `REZEPT_ZUGEORDNET`), editing a captured Rezept (`REZEPT_BEARBEITEN` → Datenprüfung → `REZEPT_ZUGEORDNET`/`ZURUECK_CHECKOUT`), another Rezept-zuerst product (`REZEPT_HINZUFUEGEN`) and the Termin (`TERMIN_WAEHLEN` → TERMINPLANUNG → `TERMIN_AUSGEWAEHLT`/`ZURUECK`) are spokes that always lead back to CHECKOUT. The Krankenkassenkarte is captured once per order (`session.krankenkasse`); a second Rezept skips it via `WEITER_KRANKENKASSE_BEKANNT`. ZUSAMMENFASSUNG and `AUFTRAG_BESTAETIGT` were **removed** (migration `0020` moved such sessions to CHECKOUT) — the binding confirmation is a checkbox on the checkout's final step.

Willkommen/Leistungsübersicht only appear when no durable consent can be taken over (first process, revoked, or changed legal texts) — see `EINWILLIGUNG_UEBERNOMMEN` below. The former separate Krankheitsbild FSM path (`KRANKHEITSBILD_ERFASSUNG/_EMPFEHLUNG`, `KRANKHEITSBILD_*` events, `eintrittspfad: 'KRANKHEITSBILD_SELBSTZAHLER'`) was **removed** (migration `0019` moved running sessions back to LEISTUNGSUEBERSICHT): Krankheitsbild discovery is sessionless now; its `krankheitsbildId` travels as optional per-product context in the Warenkorb (`WarenkorbArtikel.krankheitsbildId` → position `krankheitsbildId`, admin visibility only). The former single-product `KATALOG_PRODUKT_VORGEMERKT`/`KATALOG_PRODUKT_SELBSTZAHLER_GEWAEHLT`/`ZURUECK_KATALOG` events and `eintrittspfad` were **removed** with the Warenkorb (migrations `0020`/`0021`).

The FSM itself lives in `packages/@sanime/domain/onboarding.ts` — a workspace package imported by **both** the app and `apps/backend/` — not in `store/`, so a client-illegal transition is guaranteed server-illegal too. Read this section together with that file before touching any onboarding/scan screen or the backend's `OnboardingService`.

### State machine (`packages/@sanime/domain/onboarding.ts` + `store/onboardingStore.ts`)

- **`packages/@sanime/domain/onboarding.ts`** — pure functions only, no React/Zustand/AsyncStorage/NestJS import (isolated, imported unmodified by both runtimes):
  - `OnboardingStatus` — the 11-state union (`WILLKOMMEN`, `LEISTUNGSUEBERSICHT`, `REZEPT_AUFNAHME`, `REZEPT_PRUEFUNG`, `KRANKENKASSE_AUFNAHME`, `DATENPRUEFUNG`, `VERSORGUNGSAUSWAHL`, `TERMINPLANUNG`, `CHECKOUT`, `CHECKOUT_FEHLGESCHLAGEN`, `ABGESCHLOSSEN`), defined in `packages/@sanime/domain/types.ts` alongside `OnboardingSession` (not `types/index.ts` — that file only has a comment pointing to the new location now, no re-export).
  - `OnboardingEvent` — the event union: the original (`WEITER`, `ZURUECK`, `AGB_AKZEPTIERT`, `REZEPT_OCR_ABGESCHLOSSEN`, `FELD_KORRIGIERT`, `SUPPLY_AUSGEWAEHLT`, `KONTAKT_ERFASST`, `OTP_VERIFIZIERT`, `ZAHLUNG_ERFOLGREICH`/`AUFTRAG_EINGEREICHT` (server-only), …) plus the Warenkorb/hub events (`WARENKORB_UEBERNOMMEN { artikel, produkte }` — `produkte` is filled **only by the server** from the catalog, clients send `[]`; `REZEPT_FUER_POSITION`, `REZEPT_HINZUFUEGEN`, `REZEPT_BEARBEITEN`, `WEITER_KRANKENKASSE_BEKANNT` (like `KRANKENKASSE_UEBERSPRUNGEN`, its optional `produkte` is filled only by the server — it is the step that skips the card, so it must deliver the Versorgungsauswahl's product list), `REZEPT_ZUGEORDNET`, `ZURUECK_CHECKOUT`, `TERMIN_WAEHLEN`) and `EINWILLIGUNG_UEBERNOMMEN` (durable consent, see below). `TransitionRule.guard` receives `(session, event)` — the event is needed for guards that check payload (EINWILLIGUNG_UEBERNOMMEN only accepts the current `AGB_VERSION`/`DATENSCHUTZ_VERSION`, which now live in `packages/@sanime/domain/einwilligung.ts`; `constants/legal.ts` re-exports them).
  - `TRANSITIONS` — the actual state machine: an array of `{ from, event, to, guard? }` rows. **Every legal navigation edge, forward and backward, is an explicit row** — there is no implicit "any state can go back one step" rule and no generic fallback. If a screen dispatches an event with no matching `(from, event)` row, `transition()` returns `{ ok: false }` and nothing happens (client-side) or the backend throws a 400 (server-side) — same function, same rows, both places. When adding a new screen/step, you must add its rows here, including the `ZURUECK` row — forgetting it means the guard hook will bounce the user right back the moment they try to navigate away (this exact bug shipped twice during initial build, on the Rezept- and Krankenkasse-camera screens, before the rows were added). **`createWorkflow`'s `transition()` (`workflow.ts`) picks only the *first* rule matching `(from, event.type)`, never falls through to a second** — this is why the hub spokes need their own distinct event names (`ZURUECK_CHECKOUT` vs. `ZURUECK`, `REZEPT_ZUGEORDNET` vs. `WEITER` on DATENPRUEFUNG, `WEITER_KRANKENKASSE_BEKANNT` vs. `WEITER` on REZEPT_PRUEFUNG, `ZAHLUNG_ERFOLGREICH` vs. `AUFTRAG_EINGEREICHT`) rather than one event with different guards: two rows for the same `(from, event)` pair can never both apply, so a fork in behavior must be a fork in event name.
  - `transition(session, event)` — the reducer; validates the row exists, checks its `guard` (e.g. required-fields-present before advancing), then applies `applyEventData` (a plain `switch` merging the event's payload into the relevant session fields) and returns the new session with `status` updated.
  - `hatPflichtfelderRezept` / `hatPflichtfelderKomplett` — guard predicates on the **current scan buffer** (`session.ocrResult`), reused by `review.tsx`/`datenpruefung.tsx`. `rezeptVollstaendig(rezept)` is the same check for any Rezept; `positionenOhneRezept(session)` lists Kassenartikel still missing one. `wirdEingereicht(position)` = Kassenartikel and not `ohneRezept`; `preisBeimCheckoutEuro(position)` = self-pay price/eigenanteil; `istAbschlussfaehig(session)` = ≥1 position + a Termin + no eingereichter Kassenartikel without complete Rezept — it is part of both completion rows' guards, so the checkout's disabled state, `POST .../complete` and the Stripe webhook all apply the same rule.
  - `OnboardingSession` carries `positionen: WarenkorbPosition[]` (`{ produkt, rezept, rezeptConfidence, ohneRezept, krankheitsbildId }`, the product id **is** the position id — no duplicates), `aktivePositionId` (which position the running Rezept scan is for; `null` = Rezept zuerst) and `krankenkasse` (once per order; every position's `rezept.krankenkasse` is that one). `ocrResult`/`ocrConfidence` are only the **buffer of the running scan**, cleared when it's assigned to a position.
  - **Durable consent** (Katalogplan §2.3 — reverses the old "every Versorgung re-collects consent" rule; still needs the pending legal review, Art. 9 DSGVO): when a session's AGB+Datenschutz are both accepted in the *current* versions, the backend creates a `consent_grants` row and returns an `einwilligungsToken` once in the PATCH response; the app keeps it in SecureStore (`lib/einwilligung.ts`). The token only allows taking over that consent — it is not a session secret and opens no data. `starten()` dispatches `EINWILLIGUNG_UEBERNOMMEN { einwilligungsToken, agbVersion, datenschutzVersion }` on every fresh session; the server looks up the grant (by token hash, or by `customerId` for an already-claimed session), rejects revoked/unknown/outdated grants with 400 (app then drops the token), overwrites the claimed versions with the grant's real ones and writes new `consents` rows with `uebernommen_von_grant_id` + own IP. Revocation: `POST /consent-grants/revoke {einwilligungsToken}` (no bearer — the token is the proof; always 204), from Einstellungen → „Meine Einwilligungen“; revoking a claimed grant revokes all of the customer's grants. Logout only forgets the token locally. Claim backfills `customerId`; data export includes grants (without hash); deletion revokes them.
  - `erstelleLeereSession(id)` — the initial `OnboardingSession` factory (app-side only; the backend hydrates a domain session from its own normalized Postgres tables instead, see "Backend" below).
- **`store/onboardingStore.ts`** — the Zustand store:
  - `dispatch(event, code?)` is the single choke point every screen calls, and is **request-then-apply, never optimistic**: it runs the shared `transition()` first as a fast-fail legality pre-check only (never written to the store), then on success calls the real backend (`lib/api/onboarding.ts`'s `patch()`) and replaces `session` wholesale with the server's response — the server injects fields the client can't compute itself (server-recomputed `produkte`, `devCode`, consent `ipAdresse`). On any failure (guard rejection or network/backend error), nothing changes and the caller gets `{ ok: false, reason }`; screens funnel that into `zeigeDispatchFehler()` (`lib/onboardingNav.ts`). Persistence-after-every-step (AsyncStorage for most fields, `expo-secure-store` via `lib/secureStorage.ts` for OCR buffer, `krankenkasse`, `positionen` and contact data) and analytics instrumentation (`emitAnalyticsForTransition`) are structural side effects of a *successful* `dispatch`, not something a screen author can forget to call.
  - `STATUS_META: Record<OnboardingStatus, { route }>` — the *one* table mapping machine status to an expo-router path. Every redirect reads this table. Step counters only exist in the Rezept scan: `schrittInfo(session)` returns `{ aktuell, gesamt }` (4 steps for a position's Rezept, 6 for Rezept zuerst incl. Versorgungsauswahl/Kasse) or `null` (Kasse, Termin); `components/onboarding/ScanSchrittZaehler` renders it. `istLaufenderSchritt(status)` = a scan/Termin spoke is in progress.
  - `prozessStarten(einstieg: ClientOnboardingEvent | 'REZEPT')` — **the single entry into a process** (dashboard „Jetzt Rezept scannen“, `/einstieg`'s Rezept option, Warenkorb tab's „Zur Kasse“ with `WARENKORB_UEBERNOMMEN`). It calls `starten()`, then: consent present at LEISTUNGSUEBERSICHT → dispatch the event (`WEITER` for 'REZEPT'); still WILLKOMMEN/LEISTUNGSUEBERSICHT → stash the event in `pendingEinstiegEvent` and return that screen's route; a running spoke → resume its route; at the Kasse → 'REZEPT' becomes `REZEPT_HINZUFUEGEN`, a Warenkorb re-syncs the positions. Callers just `router.push(result.route)`.
  - `pendingEinstiegEvent` — client-only (never persisted), a „Zur Kasse“ chosen before consent exists for the session. `leistungsuebersicht.tsx`'s final "Weiter" dispatches it (if set) instead of plain `WEITER` and pushes `STATUS_META[result.session.status].route`.
  - `starten()` — calls the real `POST /onboarding-sessions`, stores the returned `sessionSecret` as the bearer token via `authStore.setToken()`, hydrates from `GET .../current`, then tries the durable-consent takeover (above); resumes an existing unfinished local session instead if one's already in memory. `app/onboarding/index.tsx`'s CTA routes by the returned status (a takeover already skipped Willkommen).
  - `dispatch()` takes a `ClientOnboardingEvent` (`@sanime/domain`), which type-level excludes the two completion events (`SERVER_EVENT_TYPES`: `ZAHLUNG_ERFOLGREICH`, `AUFTRAG_EINGEREICHT`) — completion is never a PATCH. `einreichen()` is the client's only completion action: it calls `POST .../complete` for an order with no payment due at checkout (see "Checkout: wann wird bezahlt?" below); an order with a paid self-pay share is completed only by the Stripe webhook.
  - `abschliessen()` — called only after the session is server-side `ABGESCHLOSSEN` (after `einreichen()` succeeded, or after `checkout.tsx`'s polling saw the webhook complete it), which is also why the `checkout_completed`/`onboarding_completed` analytics fire from here, not from `dispatch()`: derives a display-only `benutzer` client-side from the first position's Rezept, `session.krankenkasse` and contact data if one doesn't exist yet (`benutzer.id` is never used by any backend ownership check — those key off the bearer secret), then clears the local session **and the local Warenkorb**. **A `Supply` record does not exist before server-side completion succeeds** — matches the product rule that the binding order is only created after checkout succeeds.
- **`hooks/useOnboardingGuard.ts`** — called by every onboarding/scan screen with its own expected `OnboardingStatus` (or an array, e.g. `checkout.tsx` accepts `['CHECKOUT', 'CHECKOUT_FEHLGESCHLAGEN']`). On mismatch it `router.replace()`s to `STATUS_META[session.status].route`. This is what makes wrong-screen navigation — deep links, swipe-back, app relaunch mid-flow after a crash — structurally impossible instead of incidentally correct. Screens render `<OnboardingLoadingView />` while `!ready`. Its only option `requireOcrResult` (review/datenpruefung) requires the scan buffer; position Rezepte are checked by `istAbschlussfaehig`, not by this hook.

### Routing (`app/`)

- `app/_layout.tsx` — root `Stack`; awaits `useAuthStore().laden()` then `useOnboardingStore().laden()`, **sequentially, not `Promise.all`** — `onboardingLaden()` reads `authStore`'s bearer token to call `GET /onboarding-sessions/current`, so it's a real dependency, not just style. Declares route groups `onboarding`, `(app)`, `scan` (full-screen modal), `einstieg` (also full-screen modal — the entry chooser reachable from the dashboard's `+`), and `katalog` (a plain push stack, deliberately *not* a full-screen modal — browsing should feel like browsing, not like starting a committed process). There is no `auth` route group — see below.
- `app/index.tsx` — entry gate: splash, then if `!onboardingAbgeschlossen` — redirect to `STATUS_META[session.status].route` if an in-progress `OnboardingSession` exists (mid-flow resume after a crash/close), else `/onboarding`; else always `/(app)/dashboard`, regardless of `benutzer` — there is no forced-login gate. A `benutzer === null` visitor (never onboarded, or logged out via Einstellungen) lands on the dashboard's guest empty state; identity is only re-established later, if at all, via a Krankenkassenkarte scan matched against the real backend (`lib/api/auth.ts`'s `matchByInsuredNumber()` → `POST /customers/match`, see `app/scan/krankenkasse.tsx`'s `pruefeArchivTreffer`). A hit **claims the current session** server-side rather than issuing a new token or short-circuiting to the dashboard — the in-progress order continues normally, since the customer may be starting a *new* Versorgung, not resuming a finished one. There is intentionally no manual "log back in" screen — `app/auth/otp.tsx` was deleted because the archive-match scan is now the single identity-recovery path; don't recreate an OTP re-login screen without first checking whether that decision has changed.
- `app/onboarding/` — `index.tsx` (Willkommen; no store reads except calling `starten()`+`dispatch(WEITER)` on its own CTA) → `leistungsuebersicht.tsx` (Leistungsübersicht: **one** machine status with 3 *local* substeps — process visual, reassurance animation, AGB/Datenschutz consent — the substep counter is component `useState`, not machine state, since only the consent checkboxes carry real data; those dispatch `AGB_AKZEPTIERT`/`DATENSCHUTZ_AKZEPTIERT` immediately per tap, "Weiter" is gated on both being accepted) → `agb.tsx` / `datenschutz-text.tsx` (static legal-text screens, reachable any time via links, not part of the state machine).
- `app/(app)/` — reachable by guests and logged-in users alike (see `app/index.tsx` above). `_layout.tsx` is a plain `Stack`: `(start)/` (the home view), `einstellungen/index` and `dashboard/[id]` are pushed over it, `aufgaben` opens as a sheet **modal** (`presentation: 'modal'`, close button „Aufgaben schließen“ because the swipe alone isn't accessible); `profil` („Mein Profil“) is a sheet modal too — the one place all user data (`benutzer`: Person, Krankenkasse, Lieferadresse) is edited, as a plain form with one „Speichern“ CTA (Einstellungen only shows a „Mein Profil“ row; there is no Dokumente section — documents belong to their Versorgung). Guests can fill it in too: without a `benutzer` the data goes to `authStore.vorabProfil` (SecureStore, **not** a `benutzer` — that would mean "recognized customer" and skip the checkout OTP/load supply history); `setBenutzer()` merges it into the new `benutzer` (official Rezept/Karte/Kundenstamm values win, Vorab only fills gaps) and deletes it; checkout pre-fills phone/email from it; `abmelden()` deletes it. Read the effective profile via `useAuthStore(selectProfil)`. While `lib/vollstaendigkeit.ts`'s `profilAufgabeOffen(profil)` is true (guests included), Aufgaben lists „Profil vervollständigen“ and the bell badge counts it (`(start)/_layout.tsx` and `dashboard.tsx` must add it the same way as `aufgaben.tsx`). Profile edits are local only (`authStore.aktualisiereBenutzer`, SecureStore) — no backend sync yet. `(start)/_layout.tsx` renders `components/navigation/AppHeader` (bell left → `router.push('/aufgaben')` with the open-task badge, `SaniMeLogo` centered, gear right → Einstellungen), swipeable **Material Top Tabs** (`dashboard` = Versorgungen with the finished ones in a collapsible „Verlauf“ below, `entdecken` = catalog start, `warenkorb` = the begun-but-unsent session (one session = one product, there is no multi-item cart) with a resume/„Zur Kasse“ CTA via `STATUS_META`, plus the collapsible „Gemerkt“ list; collapsible sections use `components/dashboard/AufklappAbschnitt` — modeled on Signaro's `ModeTabBar`, custom bar in `components/navigation/StartTabBar.tsx`) and the floating center `CameraButton` (camera icon) that pushes `/einstieg`. Use expo-router's **built-in** `expo-router/js-top-tabs` (needs `react-native-tab-view` + `react-native-pager-view`, the latter native → dev-client rebuild) — do **not** add `@react-navigation/material-top-tabs`: expo-router 57 vendors react-navigation, a separate copy would bring a second navigation context. The layout loads `versorgungStore` once for all three tabs (`laedt` drives their skeletons; filters live in `lib/versorgungen.ts`). The home route is `/dashboard` — typed routes don't accept the partial-group form `/(app)/dashboard` anymore. Each tab renders a distinct guest-appropriate empty state when `benutzer` is `null` rather than placeholder identity data — match that pattern in any new `(app)` screen. The Versorgungen tab's empty-state CTA does `prozessStarten('REZEPT')` (one tap to the camera once consent is durable), with a de-emphasized "Ohne Rezept? Katalog durchsuchen" link that `router.navigate('/entdecken')`s. The Entdecken tab must not contain horizontal scrollers (they fight the tab swipe gesture). ### State (`store/`)

Independent Zustand stores; `onboardingStore` is allowed to call into `authStore` and `warenkorbStore` one-directionally (from `abschliessen()`), but not the reverse — `authStore` has no awareness of onboarding:
- `authStore.ts` — `benutzer`/`token`/`onboardingAbgeschlossen`, persisted to AsyncStorage under `sanime_*` keys, hydrated via `laden()` on app boot. `token` is the real current onboarding session's `sessionSecret` (set via `setToken()` the moment a session exists, before any `benutzer` is known) — not a fabricated login credential, and never conflated with "is this a known customer."
- `onboardingStore.ts` — see "State machine" above.
- `versorgungStore.ts` — order/supply history (`Versorgung[]`), loaded via `lib/api/supply.ts`'s `list()` and mapped through `lib/supplyMapper.ts`'s `mapSupplyRowToVersorgung()` (translates the backend's 14-status `SupplyStatus` to the app's 9-status `OrderStatus` — no backend status maps to `CANCELLED` today, that's simply unreachable from real data, not a mapping bug). A 403 (an unclaimed session has no customer to own a history) is mapped to an empty list in `laden()`, not surfaced as an error.
- `warenkorbStore.ts` — the Warenkorb *before* „Zur Kasse“: `WarenkorbArtikel[]` (product id + optional `krankheitsbildId`), SecureStore only (a cart of Hilfsmittel is health data), max `WARENKORB_MAX`, never synced except via `WARENKORB_UEBERNOMMEN`, never in analytics (`checkout_started` carries no products/count). The server never trusts it beyond the ids. Cleared by `onboardingStore.abschliessen()`. Merkliste (`merklisteStore.ts`) is separate and lives in the Warenkorb tab's collapsible „Gemerkt“.
- `scanStore.ts` **has been deleted** — its fields (photo URIs, OCR result/confidence, selected product) now live on `OnboardingSession`. If you find a reference to it, it's stale.

**Types**: `types/index.ts` still owns app-only domain types — `OrderStatus`, `Versorgung`/`TimelineEvent`/`OffeneAktion`, `Benutzer` — but `OnboardingStatus`, `OnboardingSession`, `Einwilligung`/`OnboardingConsent`, `TerminSlot`, `CustomerContact`, `Produkt`, and the OCR result/confidence shapes moved to `packages/@sanime/domain/types.ts` once the backend needed to share them (`types/index.ts` has a comment pointing there — don't redeclare them locally). Extend the domain package for anything the backend also needs to know about; keep purely app-display types (`Versorgung`, `OrderStatus`, etc.) in `types/index.ts`. The transition table/reducer logic itself belongs in `packages/@sanime/domain/onboarding.ts`, not either types file. `Produkt.hilfsmittelNr` is `string | undefined`, not required — a falsy value is exactly what marks a product as self-pay throughout the FSM (`istKassenartikel`, `istAbschlussfaehig`, `betragBeimCheckoutEuro`); `WarenkorbPosition`/`WarenkorbArtikel`/`WARENKORB_MAX` (20) live in the domain package too; `packages/@sanime/domain/krankheitsbild.ts` exports the static placeholder condition taxonomy (`KRANKHEITSBILD_KATALOG`), `findeKrankheitsbild(id)`, `matcheKrankheitsbild(transcript)`; catalog-only types (`KatalogKategorie`, `ProduktDetail`, `PassendeProdukte`, `QaEintrag`) live in `types.ts` too — see "Katalog & Discovery".

**`lib/`**: pure helpers with no React dependency —
- `api/` — the app's only networking code, one file per backend module (`client.ts`'s `request()` wraps `fetch`, attaches the bearer token from `authStore` and an `Idempotency-Key` when `idempotent: true`; `config.ts`'s `resolveApiBaseUrl()` reads `app.json`'s `expo.extra.apiUrl`; `onboarding.ts`, `auth.ts`, `supply.ts`, `catalog.ts`, `document.ts` each export plain async functions, no classes/DI — matches this repo's existing `lib/` convention, not the backend's NestJS style). `document.ts`'s `createUploadUrl`/`uploadRaw`/`register`/`getById` exist for real backend document types (approvals, invoices) but are unused by the OCR flow specifically — see the DSGVO note below. `catalog.ts`'s `listCategories`/`listProducts`/`getProduct` are properly typed against `Produkt`/a `Kategorie` interface and actually called now (`app/katalog/`) — they used to be dead code (untyped, unused) before the Katalog-Browsing feature landed.
- `voice/spracheingabe.ts` — generic `useSpracheingabe({ matcher })` (catalog uses `@sanime/domain`'s `findeHilfe`), wrapping `expo-speech-recognition`. Transcript and audio stay in React state only — never `AsyncStorage`/`SecureStore`, never sent anywhere; the final transcript lands *editable* in the search field and matches appear only as a „Meintest du …?“ question — never auto-navigation. The native module is loaded **optionally** (`requireOptionalNativeModule('ExpoSpeechRecognition')` before requiring the package, exported as `spracheingabeVerfuegbar`): a dev client built without it (the current one!) simply hides the mic instead of crashing every screen with a search field — a static import crashed the whole start view, and even a `require` inside try/catch is reported as fatal by Metro in dev. `start()` passes `requiresOnDeviceRecognition: true`, which **fails loudly** (an `error` event, surfaced as a concrete-next-step German message) if the device can't do on-device recognition, rather than silently falling back to network-based recognition — that fallback would violate the on-device-only guarantee. The native module needs `app.json`'s `expo-speech-recognition` plugin entry (already wired, injects `NSMicrophoneUsageDescription`/`NSSpeechRecognitionUsageDescription`/`RECORD_AUDIO`) and a dev-client rebuild to actually work on device — plain `expo start` / Expo Go can't load it.
- `ocr/` — real, on-device OCR (`erkenneRezept()`/`erkenneKrankenkasse()`, plus `detector.ts`, `processor.ts`, `engine.ts`, `rezeptParser.ts`, `egkParser.ts`, `validatoren.ts`, `mapper.ts`), wired into `app/scan/rezept.tsx`/`krankenkasse.tsx`. Runs entirely on-device via `expo-text-extractor`; throws `FalschesDokumentError` when the photographed document doesn't match the expected type. `rezeptParser.ts` reads Muster 16 **via its printed field labels** („Name, Vorname des Versicherten“, „Arzt-Nr.“, „Datum“, „Rp.“, „Vertragsarztstempel“ …) in Vision's reading order — that is what keeps text from other documents in the photo out — and falls back to the old keyword heuristic only when no labels are found. Muster 16 prints two-digit years (`TT.MM.JJ`, normalized to `TT.MM.JJJJ`), Nachname/Vorname on two lines (output: „Vorname Nachname“, which `abschliessen()` splits on), and the field separator often reads as a leading „1“ („102.07.26“). `high` confidence must be *earned*: by a label anchor or a check digit (LANR vs. BSNR are told apart by `pruefeLanr`, the KVNR by `pruefeVersichertenNr`, the IK by `pruefeIk`) — a falsely confident field gets a green dot and nobody re-checks it. The Rezept's Personalienfeld also yields Kasse/IK/Versicherten-Nr.: `REZEPT_OCR_ABGESCHLOSSEN` sets `session.krankenkasse` from it when none is known yet (backend mirrors this with an `insurance_policies` upsert), so `review.tsx` skips the card photo via `WEITER_KRANKENKASSE_BEKANNT` and runs the archive match (`lib/archivAbgleich.ts`) itself. `erkenneRezept()` additionally returns client-only `hinweise` (`BEREITS_EINGELOEST` from the pharmacy's billing imprint, `AELTER_ALS_28_TAGE` — Hilfsmittel-Richtlinie, pending professional confirmation) that `rezept.tsx` shows as a non-blocking Alert. Regression fixtures in `rezeptParser.test.ts` replay real Vision line order with **invented** data — real Rezept photos (`Beispielrezepte/`, gitignored) never go into the repo. `processor.ts`'s `normalisiereBild()` deliberately does *not* do perspective correction/denoise/contrast for v1 (EXIF-rotation-baking + downscale only) — see `work/Ocrintegration.md` before treating that as a bug to fix. **The original Rezept/eGK photo never leaves the device** — only the OCR-extracted fields are sent to the backend (DSGVO data minimization); `event.uri` in the dispatched onboarding events stays a purely local sandbox path the server never dereferences, and `onboarding.service.ts`'s `*DocumentId` columns stay hardcoded `null` deliberately.
- `supplyMapper.ts` — `mapSupplyRowToVersorgung()`, the one place the backend's `SupplyStatus`/row shape gets translated into the app's `Versorgung`/`OrderStatus` — see "State (`store/`)" above.
- `terminplanung.ts` — `terminAusVorschlag(slot, index)` maps the real `GET .../appointment-slots` response (`{supplierId, productId, start, end}`, no id/address) into the app's `TerminSlot` shape, marking the first (chronologically earliest) slot as "Schnellster Termin". `terminAusKalenderdatum()` is untouched, pure client-side date formatting for the manual-calendar fallback — no backend call, nothing for the server to be authoritative about.
- `mockOcr.ts` / `mockKundenArchiv.ts` **have been deleted** — the product catalog and archive-match are both real backend calls now (`lib/api/catalog.ts`, `lib/api/auth.ts`'s `matchByInsuredNumber()`). If you find a reference to either, it's stale.
- `analytics.ts` — `trackOnboarding(event)` takes a **closed discriminated union** (`OnboardingAnalyticsEvent`) with no payload slot capable of carrying OCR values, names, or diagnoses — health data is structurally unrepresentable in an event, not merely filtered at runtime. Events fire centrally from `onboardingStore.dispatch()`'s internal mapping, not from individual screens (guarantees exactly one event per real transition, and keeps the entire "no health data in analytics" surface auditable in one file).

**`constants/legal.ts`**: `AGB_VERSION`/`DATENSCHUTZ_VERSION` string constants (bump on text changes — this is the audit trail until a backend/CMS exists) plus the placeholder legal text shown on `agb.tsx`/`datenschutz-text.tsx`.

**Labels (`constants/labels.ts`)**: German user-facing copy for `OrderStatus` (label + description) plus `StatusSteps`, the canonical ordered subset of statuses used to render timelines. Status display strings belong here, not inline in components.

**Design system (`packages/@sanime/design-system`)**: an internal monorepo package — `colors.ts`, `spacing.ts`, `radius.ts`, `blur.ts`, `glass.ts`, `opacity.ts`, `shadows.ts`, `typography.ts`, `durations.ts`, `springs.ts`, `haptics.ts`, `elevation.ts` — aggregated via its `index.ts` into a `D` object (colors, spacing, radii, typography, spring presets) plus named exports like `durations`. ## Backend (`apps/backend/`)

An npm-workspaces monorepo member (root `package.json`'s `workspaces`), NestJS + Postgres/Drizzle, sharing `packages/@sanime/domain/` (the onboarding/supply/deletion-request FSMs, plain TypeScript, no NestJS import) and `packages/@sanime/design-system` (app-only, backend never imports it) with the mobile app. Neither `@sanime/domain` nor `@sanime/design-system` has a build step — `package.json`'s `main`/`types` point straight at raw `.ts` source, which is why the backend must run via `ts-node` (see the Commands section's gotcha) and why Metro resolves the app's imports of them without any special config.

**Modules** (`src/modules/`, one directory each, NestJS `@Module`-per-folder): `auth` (admin JWT + `CustomerSessionAuthGuard`, which hashes a bearer secret and looks up an `onboarding_sessions` row — there is no customer password/login, "auth" here means "which session/admin is this request"), `onboarding` (the integration module — hydrates/dehydrates the full domain `OnboardingSession` from ~7 normalized tables, the only module allowed to call `transition()` against a real request), `customer` (Krankenkassenkarte archive-match, `/customers/match`), `catalog` (products/suppliers/manufacturers/categories — plus the Ratgeber (`qa.repository.ts`) — see "Katalog & Discovery" for hierarchy, search, filters, related products and `/qa`; `catalog.mapper.ts`'s `toProdukt()` lives here, not in `onboarding/`, since `CatalogController`'s own endpoints need it directly and `onboarding` already depends on `catalog`, not the reverse), `document` (S3/MinIO presigned uploads — unused by the OCR flow specifically, see the DSGVO note above), `health-data` (OCR results + insurance policies, no controller, consumed internally only), `supply-order` (`SupplyOrderService.applyTransition()` is the single choke point for every order status change, replaying `@sanime/domain/supply.ts`'s FSM), `appointment` (`SupplierCalendarService.proposeSlots()` — real capacity-aware slot search, counts confirmed bookings only, degrades gracefully instead of throwing when a supplier is saturated), `admin` (inbox/order-management for staff), `notification` (`NotificationProvider` port, logs in dev/throws in production — never fakes delivery), `job-queue` (`InProcessJobQueue`, in-memory now but ported to swap for BullMQ later without an interface change), `verification` (OTP: `DevCodeVerificationProvider` returns the code in dev, throws in production), `consents`, `audit` (`audit_entries`/`access_logs`, `@AuditRead()` decorator), `data-export`/`deletion-requests`/`retention` (GDPR: async export bundles, pseudonymize-not-hard-delete customer erasure that retains billing/audit rows, scheduled retention enforcement), `payment` (Stripe — see "Payments (Stripe)" below), `organizations`/`idempotency`/`health` (infra: multi-tenancy, the `Idempotency-Key` middleware, the health-check endpoint).

**Multi-tenancy & ownership**: every repository extends `TenantScopedRepository` and filters by `organizationId` (`DEFAULT_TENANT_CONTEXT` today, since there's one pilot tenant — the seam exists, not yet exercised with a second org). Customer-scoped routes (supplies, orders, data-export, deletion-requests) use `resolveOwnerFilter(principal)`: an admin principal gets `null` (unrestricted), a customer principal with a real `customerId` gets scoped to it, and — critically — an **unclaimed** customer session (`customerId === null`, i.e. never archive-matched) **fails closed with a 403**, never falls through to "unrestricted." Don't reorder that logic; it was a live cross-customer data leak once, fixed in Layer 4.

**Observability** (`src/common/tracing/`, `src/common/metrics/`): both are opt-in, no-op by default (exactly like the existing `SENTRY_DSN` block in `main.ts`) — set `OTEL_EXPORTER_OTLP_ENDPOINT` for real trace export, `METRICS_ENABLED=true` (+ optional `METRICS_PORT`, default 9464) for a live Prometheus `/metrics` endpoint. `tracer.ts`'s `withSpan()` correctly handles async functions (ends the span only once the awaited work settles, not the instant the promise is created — a real bug, fixed). `metrics.ts` exports `record*(...)` functions rather than raw `Counter`/`Histogram` objects **on purpose**: unlike `trace.getTracer()`, `metrics.getMeter()` is not a dynamic proxy — an instrument created before `initMetrics()` registers a real `MeterProvider` stays permanently bound to the no-op meter, so instrument creation must be lazy (first-real-call), not module-load-time. Don't "simplify" this back to exported instrument objects; it silently breaks metrics collection with no error anywhere.

For anything not covered here — exact endpoint list, DTO/zod schemas, migration history — read `apps/backend/src/modules/<name>/` directly rather than assuming this section is exhaustive; it's a map, not the territory.

## Katalog & Discovery

Implemented from `work/worknew/Katalogplan.md` (all phases 0–7 except external legal review and the final manual QA pass). Core rule unchanged: **a client never decides whether a product is HiMi or self-pay** — the backend fills `WARENKORB_UEBERNOMMEN.produkte`/`SUPPLY_AUSGEWAEHLT.produkt` itself from the catalog (the FSM guards branch on that `hilfsmittelNr`); it 400s for a product with no available offer („… ist derzeit nicht bestellbar“), for an unknown `krankheitsbildId` context and for a Rezept scan on a self-pay position, and 404s for an unknown product.

**Data model** (`catalog.schema.ts`, migration `0018`): `catalog_categories` got `parent_id` (max two levels; products always hang on a subcategory, main categories are navigation only), `slug` (unique per org — the stable reference for static domain data), `beschreibung`, `icon` (Feather name, doubles as product image placeholder), `sort_order`, `is_active`; `krankheitsbild_id` stays and may sit on a main or subcategory (lookups expand children). `products` got `kurzbeschreibung`, `artikelnummer`, `attributes` (jsonb, filterable). New: `product_images` (public catalog images — never the health-document bucket; URL = `CATALOG_IMAGE_BASE_URL` + storage key, unset = no images), `product_variants` + `product_relations` (zubehoer/ersatzteil/dienstleistung, `source_variant_id` null = fits all variants), `qa_entries` + `qa_entry_links` (exactly one target per link: product, category, bedarf id or krankheitsbild id — the latter two not FKs, static domain data), `consent_grants`. Price/availability stay in `supplier_products`; `hilfsmittelnummer` stays on `products` (the FSM branches on it). `pg_trgm` + a trigram index on the normalized name.

**Seed** (`src/db/seed/catalog.seed-data.ts` + `qa.seed-data.ts`, pure data; `catalog.seed.ts`/`qa.seed.ts` upsert): 7 main categories, 28 subcategories, ~38 placeholder products (names end in „(Platzhalter)“, HiMi-Nr. `00.00.00.*`), one unavailable product, variants/relations on the Leichtgewicht-Rollator and the wheelchairs, 12 Ratgeber entries (own wording, real legal sources, `geprueft_am` null until editorial/legal review). `catalog.seed-data.spec.ts` is the **invariant test**: every Krankheitsbild id and every `BEDARF_KATALOG.kategorieSlugs` entry must resolve to orderable seeded products, every active subcategory needs a product, filters must match product attributes, QA links must resolve. An empty recommendation is a test failure, not a runtime state.

**Domain** (`packages/@sanime/domain/`): `bedarf.ts` (`BEDARF_KATALOG` — everyday situations, not diagnoses, referencing category *slugs*), `katalogSuche.ts` (`normalisiere` — must match the backend's `normSql` in `catalog/norm-sql.ts`; `SYNONYME`, `erweitereSuchbegriffe`, `findeBedarfe`, `findeHilfe` (Bedarfe + Krankheitsbilder ranked, used by voice/text discovery), `schlageVor` (on-device autocomplete — no request per keystroke), `schreibvorschlag` (Levenshtein typo fix for „Meintest du …?“), `rankeNachVerordnung` (splits VERSORGUNGSAUSWAHL into „Passend zu deiner Verordnung“ and „Weitere“ from the Rezept's Hilfsmittel text — word stems for German compounds, synonyms only count in name/category; a sort aid, never a preselection)), `katalogFilter.ts` (`KATALOG_FILTER` per subcategory slug with everyday labels; `pruefeFilter` used by the backend → unknown key/value = 400; `preisEuro` filters the offer price; multi-value attributes are comma lists like `innen,aussen`), `einwilligung.ts`. Hörhilfen were removed from `KRANKHEITSBILD_KATALOG` (Hörakustiker, not Sanitätshaus); `findeKrankheitsbild` returns `undefined` for legacy ids.

**API** (all public, `auth: false` in the app): `GET /catalog/categories` (`KatalogKategorie`: id, name, slug, parentId, beschreibung, icon, sortOrder — no tenant internals), `GET /products?categoryId&q&bedarfId&krankheitsbildId&filter[key]=…&limit&cursor` (main category includes children; constraints intersect; `q` = synonym expansion + `word_similarity` typo tolerance, ranked exact > synonym > category > description > trigram; filter-only text returns `[]`), `GET /products/:id` (`ProduktDetail` superset of `Produkt`: bilder, attribute, artikelnummer, varianten, kategorieSlug, verfuegbar), `GET /products/:id/related?variantId` (grouped; without variantId only universally compatible items), `GET /qa?productId|categoryId|bedarfId|krankheitsbildId|q` (exactly one; product → its category → parent category, product-specific first), `GET /qa/:slug` (+ linked products). The Rezept path's VERSORGUNGSAUSWAHL now lists only HiMi products (`nurHilfsmittel`).

**App**: screens under `app/katalog/` (see Routing), data via `lib/api/catalog.ts`/`lib/api/qa.ts`, list loading via `hooks/useKatalogSuche.ts` (debounce, stale-response cancel, screen-reader announcement „N Produkte gefunden“). Filters live in local state and are mirrored into the `filter` router param (deep links / relaunch); no new store. Product detail order is fixed: overview → „Passt das zu mir?“ (facts only, no suitability claims) → passendes Zubehör (hidden when empty) → Technische Informationen (collapsible; the only place the HiMi-Nr. appears) → Häufige Fragen; one sticky primary CTA, disabled with a reason when not orderable. **Merkliste**: `store/merklisteStore.ts`, product ids only, SecureStore only, max 40, heart on the detail page, collapsible „Gemerkt“ section in the Warenkorb start tab — never synced, never in analytics. `lib/analytics.ts`'s `supply_chosen` no longer carries a product category (health inference). `lib/einblenden.ts` and `MicButton` respect Reduce Motion.

**Not done / open**: legal review of durable consent (Art. 9 DSGVO) and Ratgeber content (HWG); no lizensierte product photos (placeholders by design); a full VoiceOver/TalkBack pass and largest-Dynamic-Type pass (plan phase 7) still has to be done by hand.

## Payments (Stripe)

`checkout.tsx`'s Zuzahlung (co-pay) charge is a real Stripe integration, not a mock — `@stripe/stripe-react-native`'s `PaymentSheet` on the app side, `apps/backend/src/modules/payment/` on the backend. Both are opt-in like every other production-only integration in this repo (Sentry, tracing, metrics): unset `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` means the backend still boots and every other feature works fine, only the payment endpoints themselves fail loudly (a real Stripe authentication error, not a silent no-op) the moment someone actually tries to use them.

**Checkout: wann wird bezahlt?** `@sanime/domain`'s `zahlungBeimCheckoutFaellig(session)` decides it: only the self-pay share of an order (positions without `hilfsmittelNr` at their offer price, plus Kassenartikel bought `ohneRezept` at `selfPayPriceCents`; `betragBeimCheckoutEuro`, server-side `selbstGezahltCents` in `onboarding.service.ts`) is paid at checkout — that's an ordinary purchase. Kassenartikel are **never** paid at checkout: the statutory Zuzahlung is collected by the Leistungserbringer later (§ 43c SGB V), after Krankenkassen-Genehmigung/delivery, since its amount isn't reliably known at order time (Befreiung § 62 SGB V, under-18s, contract prices). The FSM enforces this with two distinct `CHECKOUT → ABGESCHLOSSEN` events — `AUFTRAG_EINGEREICHT` (guard: no payment due; reached via `POST .../complete` → `OnboardingService.einreichen()`) and `ZAHLUNG_ERFOLGREICH` (guard: payment due; reached only via the webhook → `OnboardingService.abschliessenNachZahlung()`) — so `/complete` can never finish an order with a paid share and `POST .../payment-intent` 400s for an order of only Kassenartikel (and before `istAbschlussfaehig`, so nobody pays for an order that can't be submitted). Both go through the private `abschliessen()`, which runs the FSM check *before* creating **one Supply per position** (`supplyIds`; the session's/payment's `supplyId` is the first). Because the cart can change after a PaymentIntent was created: `createOrReuseIntent` reuses an intent only for the same amount (otherwise cancels it at Stripe; refuses while one is `processing`), and `abschliessenNachZahlung(…, bezahltCents)` refuses to complete if the paid amount no longer matches the order. `customerCopaySnapshotCents` on the Supply is the basis for collecting the Zuzahlung later; that later collection (invoice/SEPA, payment provider choice) is **not built yet**.

**The one rule that matters more than any other here: the mobile app never declares a payment successful.** `handleZahlung` in `checkout.tsx` creates a PaymentIntent (`POST /onboarding-sessions/:id/payment-intent`, amount computed server-side from the session's selected product — never trusted from the client) and shows Stripe's PaymentSheet. A successful `presentPaymentSheet()` only means the customer's payment method was accepted by Stripe — it does **not** complete the Versorgung. Completion (`OnboardingService.abschliessenNachZahlung()`) is called exclusively from `StripeWebhookController` (`POST /webhooks/stripe`), reacting to a `payment_intent.succeeded` event whose signature has been verified against `STRIPE_WEBHOOK_SECRET`. The app just polls (`wartenAufAbschluss`, ~10 tries × 1.2s) until the session's own status flips to `ABGESCHLOSSEN`. Don't "simplify" this into the client calling `POST .../complete` right after `presentPaymentSheet()` succeeds — that would let a client complete an order it never actually paid for, since nothing server-side would have independently verified the charge.

**Module layout** (`apps/backend/src/modules/payment/`): `PaymentsRepository` (the `payments` table — one row per Stripe PaymentIntent, `status` mirrors Stripe's own PaymentIntent.status values directly), `PaymentService` (Stripe client injected via a `STRIPE_CLIENT` factory provider — not `new Stripe(...)` inline — purely so tests can substitute a mock without real credentials or network access), `PaymentModule` (exports only `PaymentService`, imports nothing from Onboarding — same one-directional pattern as `AppointmentModule`). The webhook controller itself (`StripeWebhookController`) deliberately lives in `onboarding/controllers/`, not in `PaymentModule` — it needs `OnboardingService.abschliessenNachZahlung()`, and `PaymentModule` must never import `OnboardingModule` back (would create the exact cycle `OnboardingModule → PaymentModule → OnboardingModule`).

**Idempotency**: Stripe delivers webhooks at-least-once. `PaymentService.markSucceeded()` checks the payment row's current status before acting — a retried `payment_intent.succeeded` for an already-completed payment is a no-op, not a second completion call (which would hit an illegal FSM transition and throw). `PaymentService.createOrReuseIntent()` similarly reuses an existing reusable-state PaymentIntent for a session rather than creating a second live one — a customer backgrounding the app mid-payment and reopening it must never risk being charged twice.

**Two real bugs found while building this, both from assuming a library behaves like a sibling library**:
1. Stripe's Node SDK throws immediately at `new Stripe(apiKey)` if `apiKey` is falsy ("Neither apiKey nor config.authenticator provided") — it does **not** defer that check to the first real API call. The "unset key = no-op until used" pattern that works for Sentry/tracing/metrics doesn't work here unmodified; `PaymentModule`'s factory falls back to an obviously-fake placeholder string (`'sk_test_not_configured'`) so construction always succeeds, and an actual API call with it fails with Stripe's own real (and correctly logged) authentication error instead.
2. `NestFactory.create(AppModule, { rawBody: true })` is required in `main.ts` for `StripeWebhookController`'s `@RawBody()` to have anything to read — Stripe's HMAC signature is computed over the exact original request bytes, and Nest's default JSON body parsing (which still runs for every other route, `rawBody: true` doesn't disable it) would re-serialize the body and break verification. e2e tests exercising the webhook need the same option on `moduleRef.createNestApplication({ rawBody: true })`.

**Local/dev setup**: `apps/backend/.env` needs `STRIPE_SECRET_KEY` (a real `sk_test_...` from your own Stripe Dashboard — no code change to go live later, only swapping for `sk_live_...`) and `STRIPE_WEBHOOK_SECRET`. For local webhook delivery, run `stripe listen --forward-to localhost:3000/api/v1/webhooks/stripe` (Stripe CLI) and use the secret it prints. The app needs `app.json`'s `expo.extra.stripePublishableKey` (or `EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY`) set to the matching `pk_test_...` — safe to commit/ship client-side, unlike the secret key. **None of this repo's own testing exercises real Stripe API calls** — `payment.service.spec.ts` and `test/payment.e2e-spec.ts` both inject a mocked Stripe client for `paymentIntents.create`/`retrieve`, and verify webhook signatures for real (pure local HMAC, no network) against a throwaway `Stripe` instance. Real end-to-end verification (an actual card charge in Stripe's test mode) has not been done and needs a real Stripe test-mode account.

**Apple/Google Pay**: not enabled in this pass (card only) — `app.json`'s `@stripe/stripe-react-native` plugin entry has no `merchantIdentifier`, which only gates the *optional* Apple Pay entitlement (the plugin's other iOS step, adding a blank Swift file so the native module builds at all, is unconditional and always needed — don't remove the plugin entry entirely even if Apple Pay stays off). Adding Apple Pay later needs a registered Apple Merchant ID plus `merchantIdentifier` in the plugin config; Google Pay needs `enableGooglePay: true`. Server-side, `automatic_payment_methods: { enabled: true }` is already set unconditionally in `PaymentService.createOrReuseIntent` — it's safe regardless, Stripe only actually offers a payment method the client is configured to present.

## Manual/interactive testing

There's no automated UI test runner, and this is a native app — `npm run typecheck`/`lint` catch static errors but not navigation/state bugs (several real bugs, including one that made a screen's confirmation checkbox completely unreachable, were only caught by actually tapping through the app). For interactive verification, drive a real iOS Simulator with **`idb`** (Meta's iOS Development Bridge) rather than guessing from screenshots alone.

**One-time setup:**
```bash
brew tap facebook/fb
brew trust --formula facebook/fb/idb-companion   # required: idb-companion is an untrusted (non-default) tap
brew install idb-companion
brew install pipx
brew install python@3.11   # fb-idb's asyncio usage is incompatible with newer Python (3.12+); pin 3.11
pipx install fb-idb --python /opt/homebrew/opt/python@3.11/bin/python3.11
```
`npx expo start --ios` will try to auto-install Expo Go and typically fails in a sandboxed/no-App-Store environment ("Fetching Expo Go" → `fetch failed`) — and Expo Go generally only supports one or two recent SDKs anyway, so for this repo's SDK version it may simply be unavailable. Use a real dev build instead: `npx expo run:ios` (builds native + installs on the simulator; first run takes several minutes for CocoaPods/Xcode build).

**Per-session:**
```bash
export PATH="$PATH:/Users/lemi/.local/bin"          # idb CLI lives here after pipx install
UDID=$(xcrun simctl list devices | grep Booted | grep -oE '[0-9A-F-]{36}')
idb_companion --udid $UDID &                         # one companion process per booted simulator
idb connect $UDID <port-from-companion-stdout>       # or just `idb list-targets` to confirm "Connected"
```
Then drive it:
```bash
idb ui describe-all --udid $UDID   # dumps the accessibility tree as JSON: every AXLabel + its {x,y,width,height} frame,
                                    # in POINT space (not pixels) — same space `ui tap` expects. This is the reliable
                                    # way to find what to tap; don't eyeball coordinates from a screenshot's pixel size.
idb ui tap <x> <y> --udid $UDID
idb ui text "some text" --udid $UDID   # types into whatever TextInput is currently focused
idb ui swipe <x1> <y1> <x2> <y2> --udid $UDID   # scroll; also in point space
xcrun simctl io $UDID screenshot /tmp/out.png   # screenshot is in PIXEL space — don't mix the two coordinate systems
```
A small helper for tap-by-accessibility-label (finds the element, taps its center) is worth writing once per session — see the pattern of `describe-all` piped through a short Python script filtering by `AXLabel`.

**Gotchas hit in practice:**
- Native system sheets (the photo picker, permission dialogs) are a separate process and don't appear in `describe-all` — estimate their coordinates from a screenshot instead (convert pixel→point by dividing by the device's scale factor, e.g. 1206px / 402pt = 3.0 on an iPhone 17 Pro).
- If the app stops responding to Fast Refresh (edits not showing up after a file save), the dev-client's live Metro connection has likely dropped — `xcrun simctl terminate $UDID <bundle-id> && xcrun simctl launch $UDID <bundle-id>` fetches a fresh bundle without clearing AsyncStorage/app state.
- A floating/overlapping element (e.g. two views occupying the same screen region) doesn't always deliver taps to whichever one is visually on top — if a tap keeps landing on the wrong element despite correct-looking coordinates, that's a real hit-testing ambiguity worth flagging, not just an automation mistake.
- After adding new route files, expo-router's typed-routes declaration (`.expo/types/router.d.ts`) is normally regenerated by the dev server on file-watch; if you're editing routes without a running `expo start`, it can go stale and cause spurious `tsc` errors on `router.push('/new/route')` calls — regenerate by starting the dev server once, or via `expo-router`'s `typed-routes/generate` module directly.
- `idb` can't simulate microphone input, so `KatalogSuchfeld`'s `MicButton` can only be exercised by hand on a real device or the Simulator's own mic passthrough (and only in a dev client that includes `expo-speech-recognition`).
- `idb ui describe-all` reports frames in *content* coordinates for scrolled lists — after `idb ui swipe`, the y values don't change; tap by screenshot coordinates (pixel ÷ 3) instead.
- Watchman here sometimes stops delivering file changes to Metro (bundle stays stale even after reload): restart with `npx expo start --dev-client --clear` after `watchman watch-del <repo>`; verify by grepping the served bundle.
