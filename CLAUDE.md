# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Product context

SaniMe is a mobile app (Expo/React Native) that digitizes the German "Hilfsmittelversorgung" process (medical supply procurement via prescription + statutory health insurance). The customer just photographs documents (Rezept, Krankenkassenkarte); OCR runs entirely on-device (`lib/ocr/`), and a NestJS/Postgres backend (`apps/backend/`) handles product matching, insurance submission, and order tracking. The app runs against this real backend end-to-end — nothing in `store/` is mocked anymore (the last mocks, `lib/mockOcr.ts` and `lib/mockKundenArchiv.ts`, were deleted once the backend cutover landed). See "Backend (`apps/backend/`)" below for that side; the rest of this file covers the mobile app.

Product/UX rules that should inform any feature work:
- One task and one primary CTA per screen; always allow Back/Forward with visible progress.
- Automate over form input — never ask the user for information that could be derived (OCR, defaults, recommendations).
- Every OCR/derived field must stay user-editable; OCR output is never final.
- Error messages must state a concrete next step for the user (German, e.g. "Wir konnten dein Rezept nicht vollständig erkennen. Bitte überprüfe die markierten Felder." — not "OCR Error").
- Health/insurance data (prescription photos, diagnoses, insurance IDs) is highest-sensitivity: never log it, send it to analytics, or store it unencrypted.
- New UI must meet WCAG 2.1 AA: 44×44 touch targets, screen reader labels, logical focus order, sufficient contrast, Dynamic Type support.
- The product catalog (`Produkt` type) is a placeholder during development — never hardcode real manufacturer/pricing/Hilfsmittelnummer data as if it were production data.

## Commands

**App** (run from the repo root):
```bash
npm run start       # expo start — Metro bundler, scan QR or press i/a for simulator
npm run ios         # expo run:ios — build & launch native iOS
npm run android     # expo run:android — build & launch native Android
npm run lint        # eslint .
npm run typecheck   # tsc --noEmit
npm run test        # jest (jest-expo preset) — currently only lib/ocr/*.test.ts and packages/@sanime/domain/*.test.ts
```

`npm run lint` requires `.eslintrc.js` (extends `expo`) at the repo root — this file didn't exist before and lint silently failed with no config found; it's checked in now, don't delete it.

Jest is configured (`jest.config.js`, `jest-expo` preset) with a `test` script; run with `npm run test`. Tests are co-located next to source as `*.test.ts` — under `lib/ocr/` (parsers/validators/mapper) and `packages/@sanime/domain/` (the FSMs). No app-side integration/E2E/accessibility test automation exists — see "Manual/interactive testing" below for that.

Always run `npm run typecheck` and `npm run lint` after app changes; also run `npm run test` when touching `lib/ocr/` or `packages/@sanime/domain/`. For interactive verification (actually tapping through screens), see "Manual/interactive testing" below.

**Backend** (`apps/backend/`, proxied from the root via npm workspaces — run from the repo root, not `cd apps/backend`):
```bash
npm run backend:dev          # node --watch ts-node — NOT `nest start`/`nest build`, see the gotcha below
npm run backend:typecheck    # tsc --noEmit -p tsconfig.build.json
npm run backend:lint         # eslint "{src,test}/**/*.ts"
npm run backend:test         # jest — unit/integration, needs the docker-compose Postgres running
npm run backend:test:e2e     # jest --config ./test/jest-e2e.json
npm run backend:db:generate  # drizzle-kit generate — after any schema/*.ts change
npm run backend:db:migrate   # drizzle-kit migrate
npm run backend:db:seed      # organizations → admin → catalog → customers → retention-policy seeds, in that order
```
`docker compose -f apps/backend/docker-compose.yml up -d` starts Postgres + MinIO (S3-compatible object storage for document uploads) before `backend:dev`/`backend:test*`. Copy `apps/backend/.env.example` to `apps/backend/.env` first (`DATABASE_URL`, `STORAGE_*`, `VERIFICATION_CODE_PEPPER`, `ADMIN_JWT_SECRET` — the last two must be real values, not the checked-in placeholders, outside local dev).

**Critical gotcha**: `apps/backend/src/main.ts` boots fine under `ts-jest`/`tsx` but a plain `nest build && node dist/main.js` (or `nest start`) crashes with `ERR_MODULE_NOT_FOUND` resolving `@sanime/domain/types` — `@sanime/domain` is deliberately raw, unbuilt TypeScript (same convention as `@sanime/design-system`), and plain Node's native TS/ESM handling can't follow its extensionless internal imports the way `ts-node`'s require hook can. `start`/`start:dev` are already wired to `ts-node` for this reason — don't "fix" them back to `nest start`/`nest build`.

Always run `npm run backend:typecheck` after backend changes; run `npm run backend:test`/`backend:test:e2e` when touching anything under `apps/backend/src/modules/` or `packages/@sanime/domain/` (the FSM the backend and app both import).

## Architecture

**Stack**: Expo (SDK 54) + expo-router (file-based routing, typed routes enabled) + React Native 0.81 + NativeWind (Tailwind for RN, see `tailwind.config.js`/`global.css`) + Zustand for state + AsyncStorage for persistence. Path alias `@/*` maps to repo root (`tsconfig.json`), though existing code consistently uses relative imports (`../../types`) instead — match that convention, not the alias.

The full onboarding-to-checkout flow (Willkommen → Leistungsübersicht/consent → Rezeptaufnahme → Rezeptprüfung → Krankenkassenkarte → Datenprüfung → Versorgungsauswahl → Termin → Zusammenfassung → Checkout → Dashboard) is implemented end-to-end as an explicit **state machine**, not a hardcoded screen chain. The FSM itself lives in `packages/@sanime/domain/onboarding.ts` — a workspace package imported by **both** the app and `apps/backend/` — not in `store/`, so a client-illegal transition is guaranteed server-illegal too. Read this section together with that file before touching any onboarding/scan screen or the backend's `OnboardingService`.

### State machine (`packages/@sanime/domain/onboarding.ts` + `store/onboardingStore.ts`)

- **`packages/@sanime/domain/onboarding.ts`** — pure functions only, no React/Zustand/AsyncStorage/NestJS import (isolated, imported unmodified by both runtimes):
  - `OnboardingStatus` — the 12-state union (`WILLKOMMEN`, `LEISTUNGSUEBERSICHT`, `REZEPT_AUFNAHME`, `REZEPT_PRUEFUNG`, `KRANKENKASSE_AUFNAHME`, `DATENPRUEFUNG`, `VERSORGUNGSAUSWAHL`, `TERMINPLANUNG`, `ZUSAMMENFASSUNG`, `CHECKOUT`, `CHECKOUT_FEHLGESCHLAGEN`, `ABGESCHLOSSEN`), defined in `packages/@sanime/domain/types.ts` alongside `OnboardingSession` (not `types/index.ts` — that file only has a comment pointing to the new location now, no re-export).
  - `OnboardingEvent` — the event union (`WEITER`, `ZURUECK`, `AGB_AKZEPTIERT`, `REZEPT_OCR_ABGESCHLOSSEN`, `FELD_KORRIGIERT`, `SUPPLY_AUSGEWAEHLT`, `KONTAKT_ERFASST`, `OTP_VERIFIZIERT`, `ZAHLUNG_ERFOLGREICH`, …).
  - `TRANSITIONS` — the actual state machine: an array of `{ from, event, to, guard? }` rows. **Every legal navigation edge, forward and backward, is an explicit row** — there is no implicit "any state can go back one step" rule and no generic fallback. If a screen dispatches an event with no matching `(from, event)` row, `transition()` returns `{ ok: false }` and nothing happens (client-side) or the backend throws a 400 (server-side) — same function, same rows, both places. When adding a new screen/step, you must add its rows here, including the `ZURUECK` row — forgetting it means the guard hook will bounce the user right back the moment they try to navigate away (this exact bug shipped twice during initial build, on the Rezept- and Krankenkasse-camera screens, before the rows were added).
  - `transition(session, event)` — the reducer; validates the row exists, checks its `guard` (e.g. required-fields-present before advancing), then applies `applyEventData` (a plain `switch` merging the event's payload into the relevant session fields) and returns the new session with `status` updated.
  - `hatPflichtfelderRezept` / `hatPflichtfelderKomplett` — exported guard predicates, reused by both `review.tsx`/`datenpruefung.tsx` (to drive the "Weiter" button's disabled state) and `apps/backend`'s `OnboardingService.complete()` (defense-in-depth re-validation server-side), so the UI signal and the actual guard can never drift apart in either direction.
  - `erstelleLeereSession(id)` — the initial `OnboardingSession` factory (app-side only; the backend hydrates a domain session from its own normalized Postgres tables instead, see "Backend" below).
- **`store/onboardingStore.ts`** — the Zustand store:
  - `dispatch(event, code?)` is the single choke point every screen calls, and is **request-then-apply, never optimistic**: it runs the shared `transition()` first as a fast-fail legality pre-check only (never written to the store), then on success calls the real backend (`lib/api/onboarding.ts`'s `patch()`, or `complete()` for `ZAHLUNG_ERFOLGREICH` specifically, which is its own endpoint) and replaces `session` wholesale with the server's response — the server injects fields the client can't compute itself (server-recomputed `produkte`, `devCode`, consent `ipAdresse`). On any failure (guard rejection or network/backend error), nothing changes and the caller gets `{ ok: false, reason }`; screens funnel that into `zeigeDispatchFehler()` (`lib/onboardingNav.ts`). Persistence-after-every-step (AsyncStorage for most fields, `expo-secure-store` via `lib/secureStorage.ts` for OCR/contact data specifically) and analytics instrumentation (`emitAnalyticsForTransition`) are structural side effects of a *successful* `dispatch`, not something a screen author can forget to call.
  - `STATUS_META: Record<OnboardingStatus, { route, schritt }>` — the *one* table mapping machine status to an expo-router path and a 1–11 step number. Every redirect and every `StepCounter` in the app reads this table; there is no other place a status maps to a route.
  - `starten()` — calls the real `POST /onboarding-sessions`, stores the returned `sessionSecret` as the bearer token via `authStore.setToken()`, then hydrates from `GET .../current`; resumes an existing unfinished local session instead if one's already in memory (called once, from `app/onboarding/index.tsx`'s own CTA, and again from the tab bar's `CameraButton` for repeat orders).
  - `abschliessen()` — called only after `dispatch({type: 'ZAHLUNG_ERFOLGREICH'})` already succeeded (which is what actually calls `complete()` and creates the real `Supply`/`Order` rows server-side): derives a display-only `benutzer` client-side from the session's OCR/contact data if one doesn't exist yet (`benutzer.id` is never used by any backend ownership check — those key off the bearer secret), then clears the local session. **A `Supply` record does not exist before `complete()` succeeds** — matches the product rule that the binding order is only created after checkout succeeds.
- **`hooks/useOnboardingGuard.ts`** — called by every onboarding/scan screen with its own expected `OnboardingStatus` (or an array, e.g. `checkout.tsx` accepts `['CHECKOUT', 'CHECKOUT_FEHLGESCHLAGEN']`). On mismatch it `router.replace()`s to `STATUS_META[session.status].route`. This is what makes wrong-screen navigation — deep links, swipe-back, app relaunch mid-flow after a crash — structurally impossible instead of incidentally correct. Screens render `<OnboardingLoadingView />` while `!ready`.

### Routing (`app/`)

- `app/_layout.tsx` — root `Stack`; awaits `useAuthStore().laden()` then `useOnboardingStore().laden()`, **sequentially, not `Promise.all`** — `onboardingLaden()` reads `authStore`'s bearer token to call `GET /onboarding-sessions/current`, so it's a real dependency, not just style. Declares route groups `onboarding`, `(app)`, and `scan` (full-screen modal). There is no `auth` route group — see below.
- `app/index.tsx` — entry gate: splash, then if `!onboardingAbgeschlossen` — redirect to `STATUS_META[session.status].route` if an in-progress `OnboardingSession` exists (mid-flow resume after a crash/close), else `/onboarding`; else always `/(app)/dashboard`, regardless of `benutzer` — there is no forced-login gate. A `benutzer === null` visitor (never onboarded, or logged out via Einstellungen) lands on the dashboard's guest empty state; identity is only re-established later, if at all, via a Krankenkassenkarte scan matched against the real backend (`lib/api/auth.ts`'s `matchByInsuredNumber()` → `POST /customers/match`, see `app/scan/krankenkasse.tsx`'s `pruefeArchivTreffer`). A hit **claims the current session** server-side rather than issuing a new token or short-circuiting to the dashboard — the in-progress order continues normally, since the customer may be starting a *new* Versorgung, not resuming a finished one. There is intentionally no manual "log back in" screen — `app/auth/otp.tsx` was deleted because the archive-match scan is now the single identity-recovery path; don't recreate an OTP re-login screen without first checking whether that decision has changed.
- `app/onboarding/` — `index.tsx` (Willkommen; no store reads except calling `starten()`+`dispatch(WEITER)` on its own CTA) → `leistungsuebersicht.tsx` (Leistungsübersicht: **one** machine status with 3 *local* substeps — process visual, reassurance animation, AGB/Datenschutz consent — the substep counter is component `useState`, not machine state, since only the consent checkboxes carry real data; those dispatch `AGB_AKZEPTIERT`/`DATENSCHUTZ_AKZEPTIERT` immediately per tap, "Weiter" is gated on both being accepted) → `agb.tsx` / `datenschutz-text.tsx` (static legal-text screens, reachable any time via links, not part of the state machine).
- `app/(app)/` — reachable by guests and logged-in users alike (see `app/index.tsx` above); bottom tabs (`dashboard`, `einstellungen`) — note the custom `PremiumTabBar` in `_layout.tsx` requires `Tabs.Screen` names to match the *exact* file-based route key (`dashboard/index`, not `dashboard/index.tsx`'s folder name `dashboard`) or the title/icon silently never attach and the raw route name leaks into the tab label; `options.href: null` (used to keep `dashboard/[id]` out of the tab bar) only works with expo-router's default tab bar, so the custom bar filters visible tabs itself via an explicit route-name allow-list. Both tab screens render a distinct guest-appropriate empty state when `benutzer` is `null` rather than falling back to placeholder identity data — match that pattern in any new `(app)` screen. The tab bar has a floating center `CameraButton` that calls `onboardingStore.starten()` before pushing `/scan/rezept`, to start a **new** Versorgung (not a tab) — every new Versorgung re-collects AGB/Datenschutz consent via the onboarding machine (starts at `WILLKOMMEN`), including for repeat orders; this is a deliberate choice, not a bug, so don't "optimize" it into skipping straight to the camera without checking first.
- `app/scan/` — the full "start a Versorgung" flow, **reused for both first-time onboarding and repeat orders** (hence living under `scan/`, not `onboarding/`): `rezept` → `review` → `krankenkasse` → `datenpruefung` → `versorgungen` → `termin` → `zusammenfassung` → `checkout`. Every screen calls `useOnboardingGuard(status)` first. OCR is real, on-device (`lib/ocr/`, see below) and split across the two capture screens (prescription fields on `rezept.tsx`, insurance fields on `krankenkasse.tsx`) rather than one combined call, so `session.ocrResult` is progressively filled in; the product catalog `erkenneKrankenkasse()` used to return alongside it is now always `[]` client-side, since the backend recomputes+discards it regardless (`termin.tsx` similarly fetches real appointment slots from `GET .../appointment-slots` rather than generating them locally). `checkout.tsx` skips the phone/OTP substep entirely and jumps straight to payment if `authStore.benutzer` already exists (the repeat-order case, including one just recognized via the Krankenkassenkarte archive match) — see `hooks/useOtpVerification.ts` for the shared send/verify mechanics (its `codeSenden`/`codeVerifizieren` **are** the `dispatch()` calls for `KONTAKT_ERFASST`/`OTP_VERIFIZIERT`; `checkout.tsx` must not additionally dispatch those events itself, or one tap fires two PATCH requests), now used only by `checkout.tsx`. The payment step (`handleZahlung`) is a real Stripe integration (`@stripe/stripe-react-native`'s PaymentSheet) — see "Payments (Stripe)" below for the full picture, but the one thing to know before touching this screen: **`handleZahlung` never dispatches `ZAHLUNG_ERFOLGREICH` itself.** `presentPaymentSheet()` succeeding only means Stripe accepted the payment method: it polls the backend (`wartenAufAbschluss`) until the backend's own webhook has actually completed the session server-side. Don't "simplify" this back to an optimistic client-side dispatch — that would let a client claim a Versorgung it never paid for.

### State (`store/`)

Three independent Zustand stores; `onboardingStore` is allowed to call into `authStore` one-directionally (from `abschliessen()`), but not the reverse — `authStore` has no awareness of onboarding:
- `authStore.ts` — `benutzer`/`token`/`onboardingAbgeschlossen`, persisted to AsyncStorage under `sanime_*` keys, hydrated via `laden()` on app boot. `token` is the real current onboarding session's `sessionSecret` (set via `setToken()` the moment a session exists, before any `benutzer` is known) — not a fabricated login credential, and never conflated with "is this a known customer."
- `onboardingStore.ts` — see "State machine" above.
- `versorgungStore.ts` — order/supply history (`Versorgung[]`), loaded via `lib/api/supply.ts`'s `list()` and mapped through `lib/supplyMapper.ts`'s `mapSupplyRowToVersorgung()` (translates the backend's 14-status `SupplyStatus` to the app's 9-status `OrderStatus` — no backend status maps to `CANCELLED` today, that's simply unreachable from real data, not a mapping bug). A 403 (an unclaimed session has no customer to own a history) is mapped to an empty list in `laden()`, not surfaced as an error.
- `scanStore.ts` **has been deleted** — its fields (photo URIs, OCR result/confidence, selected product) now live on `OnboardingSession`. If you find a reference to it, it's stale.

**Types**: `types/index.ts` still owns app-only domain types — `OrderStatus`, `Versorgung`/`TimelineEvent`/`OffeneAktion`, `Benutzer` — but `OnboardingStatus`, `OnboardingSession`, `Einwilligung`/`OnboardingConsent`, `TerminSlot`, `CustomerContact`, `Produkt`, and the OCR result/confidence shapes moved to `packages/@sanime/domain/types.ts` once the backend needed to share them (`types/index.ts` has a comment pointing there — don't redeclare them locally). Extend the domain package for anything the backend also needs to know about; keep purely app-display types (`Versorgung`, `OrderStatus`, etc.) in `types/index.ts`. The transition table/reducer logic itself belongs in `packages/@sanime/domain/onboarding.ts`, not either types file.

**`lib/`**: pure helpers with no React dependency —
- `api/` — the app's only networking code, one file per backend module (`client.ts`'s `request()` wraps `fetch`, attaches the bearer token from `authStore` and an `Idempotency-Key` when `idempotent: true`; `config.ts`'s `resolveApiBaseUrl()` reads `app.json`'s `expo.extra.apiUrl`; `onboarding.ts`, `auth.ts`, `supply.ts`, `catalog.ts`, `document.ts` each export plain async functions, no classes/DI — matches this repo's existing `lib/` convention, not the backend's NestJS style). `document.ts`'s `createUploadUrl`/`uploadRaw`/`register`/`getById` exist for real backend document types (approvals, invoices) but are unused by the OCR flow specifically — see the DSGVO note below.
- `ocr/` — real, on-device OCR (`erkenneRezept()`/`erkenneKrankenkasse()`, plus `detector.ts`, `processor.ts`, `engine.ts`, `rezeptParser.ts`, `egkParser.ts`, `validatoren.ts`, `mapper.ts`), wired into `app/scan/rezept.tsx`/`krankenkasse.tsx`. Runs entirely on-device via `expo-text-extractor`; throws `FalschesDokumentError` when the photographed document doesn't match the expected type. `processor.ts`'s `normalisiereBild()` deliberately does *not* do perspective correction/denoise/contrast for v1 (EXIF-rotation-baking + downscale only) — see `work/Ocrintegration.md` before treating that as a bug to fix. **The original Rezept/eGK photo never leaves the device** — only the OCR-extracted fields are sent to the backend (DSGVO data minimization); `event.uri` in the dispatched onboarding events stays a purely local sandbox path the server never dereferences, and `onboarding.service.ts`'s `*DocumentId` columns stay hardcoded `null` deliberately.
- `supplyMapper.ts` — `mapSupplyRowToVersorgung()`, the one place the backend's `SupplyStatus`/row shape gets translated into the app's `Versorgung`/`OrderStatus` — see "State (`store/`)" above.
- `terminplanung.ts` — `terminAusVorschlag(slot, index)` maps the real `GET .../appointment-slots` response (`{supplierId, productId, start, end}`, no id/address) into the app's `TerminSlot` shape, marking the first (chronologically earliest) slot as "Schnellster Termin". `terminAusKalenderdatum()` is untouched, pure client-side date formatting for the manual-calendar fallback — no backend call, nothing for the server to be authoritative about.
- `mockOcr.ts` / `mockKundenArchiv.ts` **have been deleted** — the product catalog and archive-match are both real backend calls now (`lib/api/catalog.ts`, `lib/api/auth.ts`'s `matchByInsuredNumber()`). If you find a reference to either, it's stale.
- `analytics.ts` — `trackOnboarding(event)` takes a **closed discriminated union** (`OnboardingAnalyticsEvent`) with no payload slot capable of carrying OCR values, names, or diagnoses — health data is structurally unrepresentable in an event, not merely filtered at runtime. Events fire centrally from `onboardingStore.dispatch()`'s internal mapping, not from individual screens (guarantees exactly one event per real transition, and keeps the entire "no health data in analytics" surface auditable in one file).

**`constants/legal.ts`**: `AGB_VERSION`/`DATENSCHUTZ_VERSION` string constants (bump on text changes — this is the audit trail until a backend/CMS exists) plus the placeholder legal text shown on `agb.tsx`/`datenschutz-text.tsx`.

**Labels (`constants/labels.ts`)**: German user-facing copy for `OrderStatus` (label + description) plus `StatusSteps`, the canonical ordered subset of statuses used to render timelines. Status display strings belong here, not inline in components.

**Design system (`packages/@sanime/design-system`)**: an internal monorepo package — `colors.ts`, `spacing.ts`, `radius.ts`, `blur.ts`, `glass.ts`, `opacity.ts`, `shadows.ts`, `typography.ts`, `durations.ts`, `springs.ts`, `haptics.ts`, `elevation.ts` — aggregated via its `index.ts` into a `D` object (colors, spacing, radii, typography, spring presets) plus named exports like `durations`. This replaced the former `constants/design.ts`/`constants/colors.ts` split (both files are deleted); `D` is a 1:1-compatible import, so existing call sites didn't need to change shape. Import as `@sanime/design-system`. Every onboarding/scan screen and every `components/onboarding/*`/`components/ui/*` component uses this exclusively now — there is no second/older token system to avoid.

**Naming convention**: this codebase is German-first — identifiers, store fields, and route segments use German terms (`benutzer`, `laden`, `abmelden`, `versorgung`, `zurücksetzen`, `krankenkasse`, `rezept`). Match this convention for new domain code; don't anglicize field names.

**Components (`components/`)**: `components/ui/` holds generic building blocks (Button, Card, GlassCard, CameraButton, StatusBadge, CircularProgress, ProcessStep, SectionHeader, and now `Checkbox` + `FormField`); `components/onboarding/` holds onboarding/scan-specific composites (`DatenFeld` — the editable OCR-field-with-confidence-dot, shared by `review.tsx`/`datenpruefung.tsx`; `StepCounter`; `MiniKalender`; `OnboardingLoadingView`, the guard's loading fallback); `components/dashboard/` holds dashboard-specific composites (StatusTimeline, VersorgungCard). Business logic belongs in stores/screens, not in these UI components.

## Backend (`apps/backend/`)

An npm-workspaces monorepo member (root `package.json`'s `workspaces`), NestJS + Postgres/Drizzle, sharing `packages/@sanime/domain/` (the onboarding/supply/deletion-request FSMs, plain TypeScript, no NestJS import) and `packages/@sanime/design-system` (app-only, backend never imports it) with the mobile app. Neither `@sanime/domain` nor `@sanime/design-system` has a build step — `package.json`'s `main`/`types` point straight at raw `.ts` source, which is why the backend must run via `ts-node` (see the Commands section's gotcha) and why Metro resolves the app's imports of them without any special config.

**Modules** (`src/modules/`, one directory each, NestJS `@Module`-per-folder): `auth` (admin JWT + `CustomerSessionAuthGuard`, which hashes a bearer secret and looks up an `onboarding_sessions` row — there is no customer password/login, "auth" here means "which session/admin is this request"), `onboarding` (the integration module — hydrates/dehydrates the full domain `OnboardingSession` from ~7 normalized tables, the only module allowed to call `transition()` against a real request), `customer` (Krankenkassenkarte archive-match, `/customers/match`), `catalog` (products/suppliers/manufacturers), `document` (S3/MinIO presigned uploads — unused by the OCR flow specifically, see the DSGVO note above), `health-data` (OCR results + insurance policies, no controller, consumed internally only), `supply-order` (`SupplyOrderService.applyTransition()` is the single choke point for every order status change, replaying `@sanime/domain/supply.ts`'s FSM), `appointment` (`SupplierCalendarService.proposeSlots()` — real capacity-aware slot search, counts confirmed bookings only, degrades gracefully instead of throwing when a supplier is saturated), `admin` (inbox/order-management for staff), `notification` (`NotificationProvider` port, logs in dev/throws in production — never fakes delivery), `job-queue` (`InProcessJobQueue`, in-memory now but ported to swap for BullMQ later without an interface change), `verification` (OTP: `DevCodeVerificationProvider` returns the code in dev, throws in production), `consents`, `audit` (`audit_entries`/`access_logs`, `@AuditRead()` decorator), `data-export`/`deletion-requests`/`retention` (GDPR: async export bundles, pseudonymize-not-hard-delete customer erasure that retains billing/audit rows, scheduled retention enforcement), `payment` (Stripe — see "Payments (Stripe)" below), `organizations`/`idempotency`/`health` (infra: multi-tenancy, the `Idempotency-Key` middleware, the health-check endpoint).

**Multi-tenancy & ownership**: every repository extends `TenantScopedRepository` and filters by `organizationId` (`DEFAULT_TENANT_CONTEXT` today, since there's one pilot tenant — the seam exists, not yet exercised with a second org). Customer-scoped routes (supplies, orders, data-export, deletion-requests) use `resolveOwnerFilter(principal)`: an admin principal gets `null` (unrestricted), a customer principal with a real `customerId` gets scoped to it, and — critically — an **unclaimed** customer session (`customerId === null`, i.e. never archive-matched) **fails closed with a 403**, never falls through to "unrestricted." Don't reorder that logic; it was a live cross-customer data leak once, fixed in Layer 4.

**Observability** (`src/common/tracing/`, `src/common/metrics/`): both are opt-in, no-op by default (exactly like the existing `SENTRY_DSN` block in `main.ts`) — set `OTEL_EXPORTER_OTLP_ENDPOINT` for real trace export, `METRICS_ENABLED=true` (+ optional `METRICS_PORT`, default 9464) for a live Prometheus `/metrics` endpoint. `tracer.ts`'s `withSpan()` correctly handles async functions (ends the span only once the awaited work settles, not the instant the promise is created — a real bug, fixed). `metrics.ts` exports `record*(...)` functions rather than raw `Counter`/`Histogram` objects **on purpose**: unlike `trace.getTracer()`, `metrics.getMeter()` is not a dynamic proxy — an instrument created before `initMetrics()` registers a real `MeterProvider` stays permanently bound to the no-op meter, so instrument creation must be lazy (first-real-call), not module-load-time. Don't "simplify" this back to exported instrument objects; it silently breaks metrics collection with no error anywhere.

For anything not covered here — exact endpoint list, DTO/zod schemas, migration history — read `apps/backend/src/modules/<name>/` directly rather than assuming this section is exhaustive; it's a map, not the territory.

## Payments (Stripe)

`checkout.tsx`'s Zuzahlung (co-pay) charge is a real Stripe integration, not a mock — `@stripe/stripe-react-native`'s `PaymentSheet` on the app side, `apps/backend/src/modules/payment/` on the backend. Both are opt-in like every other production-only integration in this repo (Sentry, tracing, metrics): unset `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` means the backend still boots and every other feature works fine, only the payment endpoints themselves fail loudly (a real Stripe authentication error, not a silent no-op) the moment someone actually tries to use them.

**The one rule that matters more than any other here: the mobile app never declares a payment successful.** `handleZahlung` in `checkout.tsx` creates a PaymentIntent (`POST /onboarding-sessions/:id/payment-intent`, amount computed server-side from the session's selected product — never trusted from the client) and shows Stripe's PaymentSheet. A successful `presentPaymentSheet()` only means the customer's payment method was accepted by Stripe — it does **not** complete the Versorgung. Completion (`OnboardingService.complete()` — same method `POST .../complete` already used) is called exclusively from `StripeWebhookController` (`POST /webhooks/stripe`), reacting to a `payment_intent.succeeded` event whose signature has been verified against `STRIPE_WEBHOOK_SECRET`. The app just polls (`wartenAufAbschluss`, ~10 tries × 1.2s) until the session's own status flips to `ABGESCHLOSSEN`. Don't "simplify" this into the client calling `complete()` (or dispatching `ZAHLUNG_ERFOLGREICH`) right after `presentPaymentSheet()` succeeds — that would let a client complete an order it never actually paid for, since nothing server-side would have independently verified the charge.

**Module layout** (`apps/backend/src/modules/payment/`): `PaymentsRepository` (the `payments` table — one row per Stripe PaymentIntent, `status` mirrors Stripe's own PaymentIntent.status values directly), `PaymentService` (Stripe client injected via a `STRIPE_CLIENT` factory provider — not `new Stripe(...)` inline — purely so tests can substitute a mock without real credentials or network access), `PaymentModule` (exports only `PaymentService`, imports nothing from Onboarding — same one-directional pattern as `AppointmentModule`). The webhook controller itself (`StripeWebhookController`) deliberately lives in `onboarding/controllers/`, not in `PaymentModule` — it needs `OnboardingService.complete()`, and `PaymentModule` must never import `OnboardingModule` back (would create the exact cycle `OnboardingModule → PaymentModule → OnboardingModule`).

**Idempotency**: Stripe delivers webhooks at-least-once. `PaymentService.markSucceeded()` checks the payment row's current status before acting — a retried `payment_intent.succeeded` for an already-completed payment is a no-op, not a second `complete()` call (which would hit an illegal FSM transition and throw). `PaymentService.createOrReuseIntent()` similarly reuses an existing reusable-state PaymentIntent for a session rather than creating a second live one — a customer backgrounding the app mid-payment and reopening it must never risk being charged twice.

**Two real bugs found while building this, both from assuming a library behaves like a sibling library**:
1. Stripe's Node SDK throws immediately at `new Stripe(apiKey)` if `apiKey` is falsy ("Neither apiKey nor config.authenticator provided") — it does **not** defer that check to the first real API call. The "unset key = no-op until used" pattern that works for Sentry/tracing/metrics doesn't work here unmodified; `PaymentModule`'s factory falls back to an obviously-fake placeholder string (`'sk_test_not_configured'`) so construction always succeeds, and an actual API call with it fails with Stripe's own real (and correctly logged) authentication error instead.
2. `NestFactory.create(AppModule, { rawBody: true })` is required in `main.ts` for `StripeWebhookController`'s `@RawBody()` to have anything to read — Stripe's HMAC signature is computed over the exact original request bytes, and Nest's default JSON body parsing (which still runs for every other route, `rawBody: true` doesn't disable it) would re-serialize the body and break verification. e2e tests exercising the webhook need the same option on `moduleRef.createNestApplication({ rawBody: true })`.

**Local/dev setup**: `apps/backend/.env` needs `STRIPE_SECRET_KEY` (a real `sk_test_...` from your own Stripe Dashboard — no code change to go live later, only swapping for `sk_live_...`) and `STRIPE_WEBHOOK_SECRET`. For local webhook delivery, run `stripe listen --forward-to localhost:3000/api/v1/webhooks/stripe` (Stripe CLI) and use the secret it prints. The app needs `app.json`'s `expo.extra.stripePublishableKey` (or `EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY`) set to the matching `pk_test_...` — safe to commit/ship client-side, unlike the secret key. **None of this repo's own testing exercises real Stripe API calls** — `payment.service.spec.ts` and `test/payment.e2e-spec.ts` both inject a mocked Stripe client for `paymentIntents.create`/`retrieve`, and verify webhook signatures for real (pure local HMAC, no network) against a throwaway `Stripe` instance. Real end-to-end verification (an actual card charge in Stripe's test mode) has not been done and needs a real Stripe test-mode account.

**Apple/Google Pay**: not enabled in this pass (card only) — `app.json`'s `@stripe/stripe-react-native` plugin entry has no `merchantIdentifier`, which only gates the *optional* Apple Pay entitlement (the plugin's other iOS step, adding a blank Swift file so the native module builds at all, is unconditional and always needed — don't remove the plugin entry entirely even if Apple Pay stays off). Adding Apple Pay later needs a registered Apple Merchant ID plus `merchantIdentifier` in the plugin config; Google Pay needs `enableGooglePay: true`. Server-side, `automatic_payment_methods: { enabled: true }` is already set unconditionally in `PaymentService.createOrReuseIntent` — it's safe regardless, Stripe only actually offers a payment method the client is configured to present.

## Manual/interactive testing

There's no automated UI test runner, and this is a native app — `npm run typecheck`/`lint` catch static errors but not navigation/state bugs (several real bugs, including one that made a screen's confirmation checkbox completely unreachable, were only caught by actually tapping through the app). For interactive verification, drive a real iOS Simulator with **`idb`** (Meta's iOS Development Bridge) rather than guessing from screenshots alone.

**One-time setup:**
```bash
brew tap facebook/fb
brew trust --formula facebook/fb/idb-companion   # required: idb-companion is an untrusted (non-default) tap
brew install idb-companion
brew install pipx
brew install python@3.11   # fb-idb's asyncio usage is incompatible with newer Python (3.12+); pin 3.11
pipx install fb-idb --python /opt/homebrew/opt/python@3.11/bin/python3.11
```
`npx expo start --ios` will try to auto-install Expo Go and typically fails in a sandboxed/no-App-Store environment ("Fetching Expo Go" → `fetch failed`) — and Expo Go generally only supports one or two recent SDKs anyway, so for this repo's SDK version it may simply be unavailable. Use a real dev build instead: `npx expo run:ios` (builds native + installs on the simulator; first run takes several minutes for CocoaPods/Xcode build).

**Per-session:**
```bash
export PATH="$PATH:/Users/lemi/.local/bin"          # idb CLI lives here after pipx install
UDID=$(xcrun simctl list devices | grep Booted | grep -oE '[0-9A-F-]{36}')
idb_companion --udid $UDID &                         # one companion process per booted simulator
idb connect $UDID <port-from-companion-stdout>       # or just `idb list-targets` to confirm "Connected"
```
Then drive it:
```bash
idb ui describe-all --udid $UDID   # dumps the accessibility tree as JSON: every AXLabel + its {x,y,width,height} frame,
                                    # in POINT space (not pixels) — same space `ui tap` expects. This is the reliable
                                    # way to find what to tap; don't eyeball coordinates from a screenshot's pixel size.
idb ui tap <x> <y> --udid $UDID
idb ui text "some text" --udid $UDID   # types into whatever TextInput is currently focused
idb ui swipe <x1> <y1> <x2> <y2> --udid $UDID   # scroll; also in point space
xcrun simctl io $UDID screenshot /tmp/out.png   # screenshot is in PIXEL space — don't mix the two coordinate systems
```
A small helper for tap-by-accessibility-label (finds the element, taps its center) is worth writing once per session — see the pattern of `describe-all` piped through a short Python script filtering by `AXLabel`.

**Gotchas hit in practice:**
- Native system sheets (the photo picker, permission dialogs) are a separate process and don't appear in `describe-all` — estimate their coordinates from a screenshot instead (convert pixel→point by dividing by the device's scale factor, e.g. 1206px / 402pt = 3.0 on an iPhone 17 Pro).
- If the app stops responding to Fast Refresh (edits not showing up after a file save), the dev-client's live Metro connection has likely dropped — `xcrun simctl terminate $UDID <bundle-id> && xcrun simctl launch $UDID <bundle-id>` fetches a fresh bundle without clearing AsyncStorage/app state.
- A floating/overlapping element (e.g. two views occupying the same screen region) doesn't always deliver taps to whichever one is visually on top — if a tap keeps landing on the wrong element despite correct-looking coordinates, that's a real hit-testing ambiguity worth flagging, not just an automation mistake.
- After adding new route files, expo-router's typed-routes declaration (`.expo/types/router.d.ts`) is normally regenerated by the dev server on file-watch; if you're editing routes without a running `expo start`, it can go stale and cause spurious `tsc` errors on `router.push('/new/route')` calls — regenerate by starting the dev server once, or via `expo-router`'s `typed-routes/generate` module directly.
